# План 0.5 — кадры и оверлей живут в приложении

Статус: **сделано** (планировщик кадров в Rust, встроенный сервер оверлея). Проверка
сборки Rust — на машине с инструментами (`cargo`, `wasm-pack`): в песочнице, где
готовился план, их нет, поэтому фронтенд проверен `tsc`/`vite build`/`test:engine`,
а Rust — только чтением кода и тестами в самих модулях.

## Зачем

К 0.4 всё работало, кроме двух вещей, которые упирались в то, что кадры продвигает
окно редактора:

1. **Свёрнутое окно останавливало оверлей.** Кадры шли из `requestAnimationFrame`, а он
   в скрытом окне останавливается. В OBS картинка замирала, хотя редактор был жив.
2. **Источник браузера требовал отдельного процесса.** Релей был отдельным Node-скриптом
   (`npm run overlay:bridge`), то есть в продуктовой сборке — лишним.

## 1. Планировщик кадров в Rust

`src-tauri/src/schedule.rs`.

- Движок приложения стал общим: `Arc<Mutex<RuntimeStore>>` внутри `schedule::Shared`,
  одна блокировка на вызов ядра, поэтому `create`, `updateBase` и `tick` не пересекаются.
- Поток `rig-schedule` тикает с частотой пресета: `limited` → `fpsLimit`, «Экран» → частота
  монитора, которую фронтенд измеряет при запуске (30…240 Гц; запасной вариант — 60 Гц),
  спит до следующего срока и не догоняет пачкой, если отстал.
- Кадр уходит в окна событием `rig://frame` — это ровно тот JSON, что вернул ядро.
- Команды: `rig_schedule_start` (ручка, входы, лимитер), `rig_schedule_inputs`,
  `rig_schedule_pause`, `rig_schedule_reset_clock`, `rig_schedule_stop`,
  `rig_schedule_status`.
- Пауза не просто «не тикает»: она сбрасывает время, иначе `dt` после продолжения был бы
  равен длине паузы и все пружины дёрнулись бы.
- Фронтенд (`src/engine/nativeSchedule.ts`) присылает входы пачкой раз в 33 мс (120 мс на
  паузе) и раздаёт принятые кадры оверлеям. Готовит кадр по-прежнему фронтенд
  (`prepareFrame`), поэтому протокол оверлея и правило «один активный драйвер» не менялись.
- В браузере ничего не изменилось: `EngineBackend.native === false` — кадры идут на
  `requestAnimationFrame`.

## 2. Встроенный сервер оверлея

`src-tauri/src/overlay_server.rs`, только стандартная библиотека (новых зависимостей нет).

| Адрес | Что отдаёт |
|---|---|
| `/overlay.html` | страница оверлея из веб-сборки приложения |
| `/overlay-ws` | релей сообщений — тот же протокол, что у прежнего моста |
| `/health` | JSON: жив ли сервер, где веб-сборка, сколько клиентов |

- Слушает `127.0.0.1:17800` (как мост, чтобы ссылки не менялись); `YTP_OVERLAY_PORT`,
  `YTP_OVERLAY_HOST`, `YTP_OVERLAY_WEB` переопределяют.
- Веб-сборка ищется по порядку: `YTP_OVERLAY_WEB`, ресурсы установщика (`web/`,
  `_up_/dist/`, `dist/`), папка рядом с исполняемым файлом, `dist` и `../dist` для
  разработки. Не нашлась — сервер всё равно работает как релей и отдаёт страницу-подсказку.
- WebSocket минимальный: текст и управляющие кадры, без сжатия и расширений — ровно то,
  что присылает браузер OBS. Рукопожатие считается своим SHA-1 + base64 (тесты на векторе
  RFC 6455 внутри модуля).
- В установщик веб-сборка попадает через `bundle.resources` в `tauri.conf.json`.
- Мост `scripts/overlay-bridge.mjs` остался только для разработки в браузере: там сервера
  приложения нет.

## 3. Что проверить на своей машине

```bash
cargo test -p rig-core          # ядро не менялось, но пусть будет зелёным
cargo build -p yappytuberplus   # или: npm run tauri build
npm run tauri dev               # окно приложения
```

1. Запустить риг, открыть оверлей, свернуть окно редактора на 10–20 секунд: картинка в
   оверлее должна продолжать двигаться.
2. Диалог оверлея → «Ссылка для OBS» должна вести на `http://127.0.0.1:17800/overlay.html…`;
   вставить её в источник браузера OBS, проверить, что кадры идут без моста.
3. `http://127.0.0.1:17800/health` — `running: true`, `webRoot` указывает на ресурсы.
4. Пауза: пружины после продолжения не должны дёргаться (время сбрасывается).

## 4. Что осталось

- Нативный аудиозахват в Rust: входы по-прежнему считает WebView, и он же задаёт задержку.
- Проверка прозрачности и захвата OBS на реальной Windows-машине.
- Нагрузочный бюджет на 100–200 спрайтах.
- Текст на экране (пункт 2.6 плана 0.4) — единственный невыполненный пункт той итерации.
