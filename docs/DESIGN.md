# YappyTuberPlus: рабочий дизайн-документ

Статус: **рабочая редакция 0.1**, черновик для совместного редактирования.  
Дата: **2026-10-24**.  
Основа: «YappyTuberPlus: ригг-система», ревизия 4. Исходный документ сохранён отдельно и не изменяется.  
Целевая платформа первой версии: **Windows 10/11 x64**.  
Стек: **Tauri 2 + Rust + React + TypeScript**, редактор скриптов — **CodeMirror 6**, базовый рендер — **Canvas 2D**.  
Главный технический приоритет: **производительность, стабильный кадровый темп и предсказуемость**. Размер установщика и локальных файлов не является ограничением, но память и процессорное время всё равно контролируются.

Реализация: **MVP 0.1 собран**. Работают Rust-ядро, WASM-предпросмотр, редактор, Tauri-оболочка и автоматические проверки. Актуальные возможности и оставшиеся ограничения перечислены в `README.md`. Документ остаётся рабочим; версия документа не связана с версией формата пресета.

## 1. Цель

Лёгкий ригг для PNG-спрайтов: между PNGTuber и Live2D. Не нужны меши, деформация картинки и тяжёлый редактор. Нужны отдельные спрайты, группы, явная иерархия, формулы, реакция на микрофон и прозрачное окно для OBS.

В MVP не входят: плагины виземов, кадровая анимация спрайтов, экспорт в другие форматы, полноценный скелет с IK.

> Почему так: PNG-пайплайн остаётся простым, а иерархия и формулы дают большую часть возможностей Live2D без его сложности.


### 1.1 Критерии успеха

- Реакции спрайтов выглядят плавно при явно заданном ограничении FPS, без зависимости скорости анимации от числа кадров.
- 100–200 спрайтов с типовыми формулами не приводят к заметным рывкам на согласованном эталонном ПК; точная цель подтверждается прототипом.
- Свёрнутая или скрытая панель не останавливает оверлей, аудио и вычисления.
- Любая ошибка пользовательской формулы локализуется и не роняет кадр или приложение.
- Все действия редактора имеют один источник истины: базовая поза, скрипт и инспектор не расходятся.
- Основные операции — перемещение на сцене, изменение размеров панелей и настройка FPS — доступны напрямую, без редактирования файлов.

### 1.2 Архитектурные решения этой редакции

- Вычислитель DSL, граф зависимостей, состояние stateful-функций и санитизация реализуются **сразу на Rust**, а не переносятся туда после проблем с производительностью.
- React отвечает за редактор и панель, но не участвует в покадровом вычислении рига.
- Оверлей только запрашивает готовые кадры и рисует их. Панель и оверлей не продвигают симуляцию одновременно.
- Pull-модель остаётся базовой: видимое окно запрашивает кадр, поэтому троттлинг скрытого WebView не задаёт темп анимации.
- Аудиозахват для конечного Windows-варианта проектируется в Rust. Браузерный захват допустим для раннего прототипа, но считается готовым только после проверки в скрытом окне.
- Canvas 2D остаётся стартовым рендером. Переход на другой рендер возможен только по результатам профилирования; сама модель рига от этого не зависит.

## 2. Термины

- **Сцена** — холст и список объектов.
- **Объект** — спрайт или группа.
- **Спрайт** — картинка PNG/WebP с пивотом и базовой позой.
- **Группа** — объект без картинки; содержит другие объекты, имеет пивот и скрипт.
- **Базовая поза** — статичные значения, выставленные в редакторе.
- **Динамическое значение** — результат формул за текущий кадр.
- **`inherit`** — значение того же параметра у родителя.
- **`parent`** — алиас родительского объекта для доступа к любому его параметру.
- **`offset`** — вектор от пивота родителя к пивоту объекта в базовой позе.
- **Вход** — значение из микрофона, времени, моргания и т.п.
- **Сигнал** — число, которое записывает плагин.
- **Глобальная переменная** — именованное число, вычисляемое до объектов.

## 3. Модель данных

```ts
type ParamName =
  | "x" | "y" | "rotation"
  | "sizeX" | "sizeY"
  | "skewX" | "skewY"
  | "opacity" | "visible" | "layer";

interface Vec2 {
  x: number;
  y: number;
}

interface BasePose {
  x: number;        // px, позиция пивота в сцене
  y: number;        // px
  rotation: number; // градусы, по часовой стрелке
  sizeX: number;    // множитель, 1 = исходный размер
  sizeY: number;
  skewX: number;    // градусы
  skewY: number;
  opacity: number;  // 0..1
  visible: number;  // исходное 0/1 для генерации скрипта
  layer: number;    // исходный слой для генерации скрипта
}

interface RigObject {
  id: string;                 // ASCII: a-z, 0-9, _
  name: string;               // отображаемое имя
  kind: "sprite" | "group";
  enabled: boolean;           // доступность для показа, умножается на visible из скрипта
  image: string | null;       // null у группы
  parentId: string | null;    // скрытое поле; задаётся только деревом
  pivot: Vec2;                // UV 0..1; у группы только производное UI-значение
  base: BasePose;
  script: string;             // локальный скрипт объекта
}

type FpsMode = "limited" | "display";

interface RuntimeConfig {
  fpsMode: FpsMode;           // по умолчанию "limited"
  fpsLimit: number;           // целое 1..240, по умолчанию 60
}

interface RigPresetV2 {
  version: 2;
  name: string;
  canvas: { width: number; height: number };
  objects: RigObject[];       // порядок в структуре — tie-break для слоёв
  globals: string;            // глобальные переменные
  runtime: RuntimeConfig;
  audio: AudioConfig;
  overlay: OverlayConfig;
}

// Не входит в пресет: это локальная раскладка конкретного пользователя.
interface EditorLayout {
  version: 1;
  leftWidth: number;
  rightWidth: number;
  sceneHeight: number;
  inspectorHeight: number;
  diagnosticsHeight: number;
  leftCollapsed: boolean;
  rightCollapsed: boolean;
  diagnosticsCollapsed: boolean;
}

interface EditorSessionV1 {
  version: 1;
  currentPreset: string | null;
  layout: EditorLayout;
  sceneZoom: number;
  scenePan: Vec2;
  window: WindowConfig;
}
```

Правила:

- `id` уникален, стабилен и используется в формулах.
- `parentId` — скрытое служебное поле. Оно не показывается в инспекторе и не доступно из скрипта; родитель задаётся только перетаскиванием или выбором в дереве.
- `objects` хранит и спрайты, и группы. Группы не рисуются.
- `script` есть у каждого объекта. Общего скрипта на весь пресет нет.
- `globals` — отдельный текст для глобальных переменных.
- `pivot` — UV-координата спрайта; может выходить за 0..1. В геометрию всегда переводится в пиксели.
- `layer` есть и у группы. Дети по умолчанию наследуют слой.
- Порядок отрисовки: сначала по `layer` (меньше — дальше), при равном слое поверх тот объект, который **выше в структуре**; потомок всегда поверх своего предка. Поэтому строки дерева можно переставлять (drag за верхнюю/нижнюю четверть строки, `Alt+↑` / `Alt+↓`) — это меняет не только список, но и то, кто кого перекрывает. Перетаскивание в середину строки по-прежнему вкладывает объект внутрь. Движок сортирует по `layer` и порядку массива, поэтому итоговый порядок редактор пересобирает сам (`applyTreeOrder` в `src/engine/frame.ts`) — и для сцены, и для оверлея кадр уходит уже переупорядоченным.
- Старые `influences` и веса отсутствуют.
- `runtime` принадлежит пресету: перенос пресета сохраняет выбранный режим FPS.
- `EditorLayout` принадлежит сессии и никогда не записывается в пресет. Смена раскладки не делает пресет изменённым.
- `base.visible` и `base.layer` задают исходные литералы для генерации или сброса соответствующих строк скрипта. Во время кадра используются вычисленные `visible` и `layer`; двойного прибавления базового слоя нет.
- `enabled` — отдельный от скрипта флаг «доступен для показа». Итоговая видимость = `visible × enabled`, причём выключенный родитель гасит всё поддерево. Глаз в структуре меняет только `enabled`, поэтому формулы объекта (`visible = blink > 0 ? 1 : 0` и подобные) остаются нетронутыми, а временно скрытый объект возвращается в кадр с прежним поведением. Флаг не входит в DSL и не может быть изменён из скрипта; движок его не знает — кадр фильтруется в редакторе перед отрисовкой и перед отправкой в оверлей.

> Почему так: скрипт на объект убирает стену текста, группа как объект даёт общий скрипт и наследование, а явный `parentId` заменяет веса без потери контроля.

## 4. Координаты, база и динамика

`base` — статичная поза в координатах сцены. Динамические значения добавляются к ней:

```text
итог.x        = base.x + x
итог.y        = base.y + y
итог.rotation = base.rotation + rotation
итог.sizeX    = base.sizeX * sizeX
итог.sizeY    = base.sizeY * sizeY
итог.skewX    = base.skewX + skewX
итог.skewY    = base.skewY + skewY
итог.opacity  = limit(base.opacity * opacity, 0, 1)
итог.visible  = visible
итог.layer    = layer
```

- `x`, `y` — пиксели.
- `rotation`, `skewX`, `skewY` — градусы, положительное направление по часовой стрелке.
- `sizeX`, `sizeY` — множители; `0` схлопывает спрайт, отрицательное значение зеркалит.
- `opacity` — множитель.
- `visible` — строго 0 или 1; дробные значения округляются и дают диагностическое предупреждение. Для плавности есть `opacity`.
- `layer` — число; сортировка по возрастанию, затем по порядку в `objects`.
- Пивот — точка вращения и масштаба. `base.x/base.y` — позиция пивота в сцене.

### 4.1 Пространства и единицы

Есть три разных пространства, и их нельзя смешивать:

1. **Сцена** — пиксели, начало в левом верхнем углу холста, `+x` вправо, `+y` вниз. В этих единицах работают `base.x/y`, `x/y`, `offset`, все векторные функции и `width/height`.
2. **UV** — только `pivot` спрайта: доли 0..1 по осям картинки. UV не является евклидовым вектором: длина и угол в UV зависят от соотношения сторон.
3. **Локальные пиксели картинки** — то, что рисуется относительно пивота.

Пивот переводится в пиксели до любой геометрии:

```text
pivotPx = vec(pivot.x * width, pivot.y * height)
drawImage(image, -pivotPx.x, -pivotPx.y, width, height)
```

Для группы картинки нет: её пивот — это `base.x/y`, а UV-доля вычисляется из границ только для интерфейса. В геометрии группа использует `base.x/y` напрямую.

Почему аспект не «плывёт»: UV-координата не участвует в `vlen`, `rotate`, `vangle` и подобных функциях. Сначала каждая ось переводится в пиксели, и только потом считается вектор. Например, картинка 200×100 с пивотом `(0.5, 1)` даёт `pivotPx = (100, 100)`. При повороте спрайта вокруг этой точки пиксельная геометрия остаётся корректной; «плывёт» только тот код, который попытался бы считать UV как обычный вектор.

Пример с соотношением 2:1: сдвиг `0.5` по X — это `100 px`; после поворота на 90° те же `100 px` идут по Y, а в UV по высоте это уже `1.0`. Поэтому UV нельзя вращать напрямую: сначала `pxv`, затем `rotate`, затем при необходимости `uvv`.

Для явных переводов есть:

```text
px(n, size)       // UV -> px по одной оси
uv(value, size)   // px -> UV по одной оси
pxv(v, sizeVec)   // UV-вектор -> px-вектор
uvv(v, sizeVec)   // px-вектор -> UV-вектор
```

Размеры доступны только для чтения:

| Имя | Значение |
|---|---|
| `width`, `height` | размер исходной картинки спрайта в px; для группы — размер её границ |
| `canvasWidth`, `canvasHeight` | размер холста в px |

Правило единиц: все векторы в формулах — пиксели сцены. `vlen(v)` возвращает пиксели, `vnorm(v)` — безразмерное направление, `vdot(a, b)` — px², `vangle(a, b)` — градусы. Вызывать `vlen` на UV-значениях нельзя: результат не будет иметь физического смысла при неквадратном спрайте.

`x` и `y` остаются отдельными скалярными параметрами в пикселях. Векторные выражения — промежуточные: `follow(...)` возвращает вектор, `.x`/`.y` читают его компоненту. Это не создание объекта, а обычный доступ к полю вектора, как `offset.x`.

> Почему так: пиксели — единственная общая единица для позиций, поворотов и векторов; UV остаётся только там, где он удобен автору, и не протекает в математику.

## 5. Иерархия

### 5.1 `parent` и `inherit`

У объекта один родитель. В скрипте доступны:

- `parent.x`, `parent.y`, `parent.rotation`, `parent.sizeX`, `parent.sizeY`, `parent.skewX`, `parent.skewY`, `parent.opacity`, `parent.visible`, `parent.layer` — динамические значения родителя в текущем кадре, то есть результат его скрипта без `base`.
- `inherit` — то же самое, что `parent.<текущий параметр>`. Для `x` это `parent.x`, для `rotation` — `parent.rotation`.

`parent.<param>` не подставляет итоговую мировую позу: база ребёнка уже задана абсолютно в координатах сцены. Наследуется только динамика, иначе ребёнок прибавил бы к своей базе ещё и базу родителя.

`inherit` не суммирует веса и не ссылается на конкретное поле другого объекта. Если нужен другой параметр, пишется `parent.rotation` или `torso.y` — параметр любого объекта сцены доступен по его имени, а `torso.parent.size_x` поднимается на одну ступень к родителю названного объекта. Чужой параметр читается в текущем кадре; если объекты ссылаются друг на друга по кругу, ядро берёт значение прошлого кадра и пишет в диагностику «цикл зависимости». В глобальных переменных объекты по-прежнему не видны: они вычисляются раньше сцены.

### 5.2 `offset` и `follow`

Для объекта с родителем:

```text
offset = vec(base.x - parent.base.x, base.y - parent.base.y)
```

Это вектор от пивота родителя к пивоту объекта в базовой позе.

`follow` возвращает **дополнительное смещение**, которое даёт динамический поворот и масштаб родителя:

```text
follow(v, parent) = rotate(vscale(v, parent.sizeX, parent.sizeY), parent.rotation) - v
vscale(v, sx, sy) = vec(v.x * sx, v.y * sy)
```

Вычитание `v` обязательно: базовая поза уже содержит исходный вектор, поэтому добавляется только изменение от динамики. Без вычитания объект уехал бы на двойной offset.

Для чистого поворота есть короткая форма:

```text
orbit(v, angle) = rotate(v, angle) - v
```

`follow` и `orbit` возвращают вектор. Запись `follow(offset, parent).x` означает «взять X-компоненту результата»; это не создание объекта и не вызов метода. Аналогично `offset.x` и `vec(1, 2).y`.

**Базовая поза и дети.** Динамика передаётся детям сама, а базовая поза хранится абсолютно —
поэтому редактор переносит базы потомков, когда родитель меняет позу в инспекторе: сдвиг
сдвигает, поворот поворачивает вокруг пивота родителя (`base.x/base.y`), масштаб масштабирует.
Так группа не «отклеивается» от своих детей: без этого дети не меняли ни угол, ни место, пока
родителя не начинали анимировать скриптом. Потомок, выделенный вместе с родителем, правится
один раз — его базу задаёт та же операция. Логика живёт в `src/engine/structure.ts`
(`propagateBase`) и покрыта node-тестами.

**Порядок отрисовки.** Сцена и оверлей сортируют спрайты перед каждой отрисовкой: сначала
`layer` (базовый или из скрипта), при равенстве — структура (`frontness`: верхняя строка
поверх нижней, потомок поверх предка). Массив `frame.order` движка для этого больше не нужен:
смена слоя в инспекторе действует сразу, не дожидаясь перезапуска движка, и одинаково на паузе.

### 5.3 Скрипты, чужие объекты и события

Скрипт (`globals.rig` и скрипт любого объекта) состоит из обычных присваиваний и блоков
событий. Присваивание каждый кадр задаёт одно значение:

```text
x = 200                 # свой параметр объекта или глобальная переменная
head.rotation = 15      # чужой объект: объект.параметр
```

Блок события:

```text
on <условие> {
  имя = выражение
  чужой_объект.параметр = выражение
}
```

Условий три вида:

| Условие | Смысл |
|---|---|
| `start` | первый кадр после запуска и после «Стоп» |
| `<модуль>.<вход>.<тип>` | прямой вход модуля: `mouse.left.down`, `mic.talking.hold(0.5)` |
| `<имя>` | именованное событие из `trigger имя = модуль.вход.тип` |

`trigger` разрешён только в глобальном скрипте: имя одно на сцену, и на него подписываются
скрипты любых объектов. Префикс `event.` необязателен и остаётся синонимом прямого входа.
Тип внутри пути отделяется справа с учётом скобок: `hold(0.5)` не ломает разбор на точки.

Разбор — в парсере (`parse_script` → `Script { assignments, events, triggers }`), исполнение —
в рантайме, до вычисления формул. Порядок кадра:

1. события: сработавшие блоки пишут значения в кэш кадра;
2. записи чужим объектам из обычных присваиваний (`writes`);
3. глобальные переменные и параметры объектов — формулы видят уже записанные снаружи значения.

Запись чужому объекту кладётся в кэш до формул, поэтому собственная формула этого параметра
в кадре не считается: параметр принадлежит записи. Если запись стоит в теле события, она
действует только в кадр срабатывания, и со следующего кадра снова работает формула.

Значение входа сравнивается с прошлым кадром; для `hold`/`relax` рантайм держит момент начала
удержания, номер кадра, на котором условие выполнилось, и защёлку «уже сработало». Удержание
срабатывает **на кадр позже**, чем его условие стало истинным: защёлка хранит номер кадра
включения, и тело выполняется только когда `seq` больше этого номера. Поэтому `hold(0)` и
`relax(0)` отличаются от `down` и `up` — это не фронт, а «следующий кадр». Порог «включено» у
всех типов один (`> 0.5`), второго аргумента у `hold`/`relax` нет.

Кэш кадра — ключевая деталь: значение из события читается всеми, кто обращается к переменной
в этом же кадре (объекты видят новое значение сразу), но на следующем кадре кэш очищается, и
обычная формула или прошлое значение снова берут верх.

Переменная, которую меняют только события, попадает в `persistent_globals`: у неё нет
выражения, и `eval_node` отдаёт значение прошлого кадра. Так `a = !a` не превращается в цикл:
левая часть — новое значение, правая — прошлое. Явная запись того же самого — `state.имя`:
ядро отдаёт значение прошлого кадра для глобальной переменной, своего параметра или чужого
объекта.

Состояние событий (`event_state`) и флаг «первый кадр» сбрасываются по **Стоп** и при
перезапуске движка: редактор пересоздаёт ядро, поэтому первое нажатие после остановки снова
считается первым, а `on start` срабатывает заново.

**Ошибки не останавливают сцену.** `parse_script` возвращает `ScriptError { line, column,
length, message }`, и `Rig::new` складывает такие ошибки в `compile_diagnostics`: скрипт с
ошибкой не участвует в кадре, а сообщение видно в диагностике. Тот же разбор отдаёт запрос
`check` — редактор подчёркивает ровно указанный диапазон и показывает текст ошибки под
скриптом.

### 5.4 Скрипт по умолчанию

Корневой объект:

```text
x = 0
y = 0
rotation = 0
sizeX = 1
sizeY = 1
skewX = 0
skewY = 0
opacity = 1
visible = <текущий base.visible>
layer = <текущий base.layer>
```

Объект с родителем:

```text
// follow(...) возвращает вектор; .x/.y берут его компоненты
x = inherit + follow(offset, parent).x
y = inherit + follow(offset, parent).y
rotation = inherit
sizeX = inherit
sizeY = inherit
skewX = inherit
skewY = inherit
opacity = inherit
visible = inherit
layer = inherit
```

Это готовая иерархия: ребёнок следует за переносом, поворотом и масштабом родителя. Если нужно другое поведение, формула заменяется вручную.

Ограничение: родительский `skew` не двигает позицию ребёнка. Наследуется только собственный `skew`. Для сложных случаев можно добавить формулу вручную.

### 5.5 Пружинная цепочка (хвост, лента, усы)

Цепочка не добавляет в движок ни нового типа объекта, ни отдельного «физического» состояния:
она собирается из иерархии и обычных stateful-функций. Редактор лишь расставляет родителей и
пишет сегментам скрипт — тот же, что автор мог бы написать руками.

Сегмент `i` цепочки (0 — ближайший к корню):

```text
x = inherit + follow(offset, parent).x
y = inherit + follow(offset, parent).y
rotation = spring(inherit + bend_i + noise(seed_i, 0.3) * sway, f_i, d_i)
sizeX, sizeY, skewX, skewY, opacity, visible, layer = inherit
f_i = max(0.4, f * (1 - 0.08 * i))
d_i = min(0.95, d + 0.03 * i)
```

- **Почему это волна.** Цель пружины — угол родителя *в этом кадре*. Пружина доходит до цели
  не мгновенно, поэтому сегмент отстаёт от родителя; следующий сегмент отстаёт от предыдущего,
  и возмущение от корня бежит к кончику с нарастающей задержкой. Никакого «предыдущего кадра»
  вручную не нужно: отставание даёт сама пружина.
- **Почему частота падает к кончику.** У длинного хвоста кончик догоняет медленнее и с большим
  затуханием — так он не дребезжит на высокой частоте и не «щёлкает» на границе кадра.
- **Покачивание в покое** — `noise` внутри цели пружины, а не поверх угла: шум сглаживается
  пружиной и не выглядит дрожью.
- **Шарнир.** Пивот сегмента ставится на верхнюю кромку (`y = 0.06`). Так как спрайт рисуется от
  `-pivot * размер`, смена пивота сдвинула бы картинку, поэтому база сдвигается на
  `R(base.rotation) · Δpivot · размер` — спрайт остаётся на месте, а вращение идёт по стыку.
- **Корень без родителя не переписывается:** `inherit`/`offset` требуют родителя, а движение
  корня — это движение персонажа. У корня, у которого родитель есть, пружина тоже ставится.
- Порядок сегментов — порядок выделения (`selection`), а не порядок строк в дереве: автор сам
  решает, что считать корнем.

Реализация: `src/engine/chain.ts` (`buildChain`, `chainScript`, `hingeBase`), диалог —
`src/components/ChainDialog.tsx`, кнопка — панель структуры. Всё изменение уходит в историю
одним шагом («Пружинная цепочка»), поэтому Ctrl+Z возвращает связи, пивоты и скрипты.

### 5.6 Пресет поведения (вкладка «Поведение»)

Поведение — это не новый слой движка и не поле пресета, а **генератор формул**: вкладка
превращает ползунки в блок присваиваний в начале скрипта объекта. Истина одна — текст скрипта.

Формат блока:

```text
// ── поведение: вкладка «Поведение» ──
// @behaviour {"smooth":0.4,"spring":0.7,"bounce":60,"rotationalLimitLeft":5,"rotationalLimitRight":40,…}
x = spring(smooth(inherit + follow(offset, parent).x + sin(time * 2 * pi * 1.2 + 2.827) * 10, 104), 2.24, 0.45)
y = spring(smooth(inherit + follow(offset, parent).y - mic.speak * 60, 104), 2.24, 0.45)
rotation = spring(smooth(inherit, 104), 2.24, 0.45) + limit(spring(smooth(mic.speak * 12, 104), 2.24, 0.45), -5, 40)
sizeY = inherit * (1 + smooth(mic.speak * 0.8, mic.speak * 0.8 > (state.sizeY - inherit) ? 90 : 240))
sizeX = inherit * 2 - sizeY
visible = ((mic.talking > 0 or mic.speak > 0.05) ? 1 : 0) * (1 - auto.blink)
// ── конец поведения ──
```

Правила:

- **Метаданные — в комментарии.** `// @behaviour {…}` хранит сами настройки, поэтому вкладка
  читает их обратно и ничего не расходится с кодом. Отдельного поля в `RigObject` нет: блок и
  настройки — один объект данных, их нельзя потерять по отдельности.
- **Генерируется только то, что отличается от поведения по умолчанию.** Пустые ползунки не
  пишут строк — иначе блок затирал бы авторские формулы.
- **Конфликты снимаются.** Если блок задаёт параметр (`x`, `y`, `rotation`, `sizeX`, `sizeY`,
  `visible`), одноимённые присваивания вне блока удаляются, но только на верхнем уровне скрипта:
  строки внутри `on … { }` не трогаются. Всё изменение уходит в историю одним шагом.
- **Отображение «сила → параметры».** Сглаживание: `halflife = 260 мс × сила`. Пружина:
  `frequency = 4.5 − 3.8 × сила`, `damping = 0.85 − 0.6 × сила` — «сильнее» значит мягче и
  качается дольше. Так ползунок остаётся одним числом 0..1, но за ним стоят физические единицы.
- **Фильтр стоит после сборки цели, а не на `follow`.** Позиция считается как
  `inherit + follow(offset, parent) + покачивание − подпрыгивание`, и уже эта сумма уходит в
  `smooth`/`spring`. Поэтому «drag» гасит реакцию объекта в абсолюте: и наследство родителя, и
  подпрыгивание, и покачивание, — а не только следование за родителем. У объекта без родителя
  (цель `0`) фильтр тоже работает: пружина и сглаживание видны на bounce и довороте.
- **Поворот фильтруется по частям.** Наследуемый угол (`inherit` или `0`) и собственный доворот
  от речи фильтруются **двумя независимыми цепочками** с отдельными узлами состояния. Это не
  оптимизация, а условие честного предела: `limit` стоит на довороте, поэтому ограничивает
  именно отклонение, а не сумму с углом родителя. Если поставить фильтр на сумму, поворот
  родителя на 30° съедал бы бюджет предела и «ноль влево» перестал бы быть запретом.
- **Предел доворота — два числа.** `rotationalLimitLeft` и `rotationalLimitRight` — пределы
  отклонения влево и вправо. Ноль с одной стороны означает честный запрет (`limit(v, 0, 40)`),
  а не «предела нет»: если не заданы оба, ограничения не пишутся вовсе. Старое поле
  `rotationalLimit` (единое ±) читается как оба числа — пресеты не ломаются молча.
- **Подпрыгивание.** `y` получает `− mic.speak × bounce` (минус — вверх). Без внешнего фильтра
  (сглаживания и пружины позиции) подпрыгивание заворачивается в собственную пружину
  `spring(…, 2.2, 0.55)`, иначе объект дёргался бы на каждом кадре речи. С включённым фильтром
  отдельная пружина не нужна: скорость подпрыгивания задаёт уже он.
- **Покачивание — синусоида по умолчанию.** `sin(time * 2π * f + φ)` с фазой из id объекта:
  движение повторяемое и одинаковое при каждом запуске. Галочка «Случайно» меняет формулу на
  `noise(seed, f) * амплитуда` — шум не повторяется. Фаза `(seed mod 100) / 100 × 2π`, у `y`
  seed на единицу больше, поэтому оси не качаются синхронно.
- **Сквош без локальных переменных.** В скрипте объекта имя слева — это параметр, поэтому
  временную переменную завести нельзя. Прошлое значение сквоша берётся из `state.sizeY`:
  `sizeY = inherit × (1 + s)`, значит `s_prev = state.sizeY − inherit`. Отсюда же асимметрия:
  если цель больше прошлого значения — работает скорость деформации, иначе скорость возврата.
  `sizeX` считается из `sizeY` как `2 × inherit − sizeY`, чтобы обе оси были согласованы.
- **Видимость.** Три состояния на канал: `×` — не управлять, `открыт` — виден при речи /
  открытых глазах, `закрыт` — в тишине / на моргании. Несколько условий перемножаются.
- **Числа вводятся руками.** Значение справа от ползунка — поле ввода: клик открывает его, точка
  и запятая равнозначны, значение зажимается в границы ползунка. Пока поле в фокусе, панель
  показывает черновик, поэтому «0.05» можно набрать по цифрам и не потерять точку.

Физика поворота (`phys rotation`) — единственная «физика» в пресете. Она разворачивает спрайт
«тяжёлой» стороной (той, что дальше от пивота) в заданный угол: цель пружины —
`угол − тяжесть(pivot) − base.rotation`, где `тяжесть(pivot)` — угол вектора от пивота к центру
спрайта в системе «0° вниз, 90° вправо». При пивоте по центру вектор нулевой — физика выключена,
и панель об этом пишет.

Система координат — переключатель `physSpace`, потому что «физика» бывает двух разных вещей:

- `world` (мировая) — цель `spring(угол − тяжесть − base.rotation)`. Угол живёт в мире:
  спрайт **не** едет за поворотом тела, поэтому подвеска, серьга или прядь висят по мировой
  вертикали, пока тело наклоняется. Цель постоянна, значит пружина только доводит спрайт до
  неё и больше ни на что не реагирует;
- `parent` (родительская) — цель `spring(inherit + угол − тяжесть − base.rotation)`. Угол задан
  **внутри** тела: поворот родителя входит в цель, тело подхватывает спрайт, а пружина
  запаздывает — получается маятник. Так ведёт себя рука на плече: она едет с телом, отстаёт и
  качается, а потом успокаивается.

Разница принципиальная: параметры объекта не наследуют угол родителя автоматически (наследуется
только поза через `follow`), поэтому `inherit` в формуле — это единственный способ «прикрепить»
угол к телу. Без него мировая физика выглядит как спрайт, который перестал вращаться вместе с
телом, — это ожидаемо, но для конечностей обычно нужен `parent`.

`phys squash` (сжатие по направлению абсолютного движения) и `phys move` (гравитация для
падающих объектов) в этой редакции не реализованы. Им нужны скорость в мировых координатах и
собственное состояние на объект; первое требует сложения трансформаций по иерархии в рантайме,
второе — нового вида stateful-узла (сейчас состояние есть только у `smooth`, `spring` и у
событий). Реализация — через `NodeKey::Param(object, param)` с производной по времени и
отдельным списком «физических» объектов; пресет поведения в этом случае останется генератором,
но формулы станут вызовами `phys_*`.

### 5.4 Прикрепление и открепление

- При прикреплении к родителю нейтральные строки (`0`, `1`, текущий `base.layer`) заменяются на скрипт по умолчанию для ребёнка.
- Пользовательские строки не перезаписываются.
- При откреплении строки, совпадающие со скриптом по умолчанию, возвращаются к нейтральным значениям.
- Если в пользовательской строке остались `inherit`, `parent` или `offset`, редактор показывает ошибку: их нужно заменить.
- При смене родителя `inherit` и `parent` автоматически указывают на нового родителя, `offset` пересчитывается.
- При удалении родителя дети переходят к родителю удалённого. Ссылки на удалённый `id` в скриптах заменяются на нового родителя.

> Почему так: `inherit` остаётся простой ссылкой, а `offset` + `follow` дают настоящий поворот вокруг пивота родителя без скрытых мировых матриц.

## 6. Скрипты

- Одна строка — одно присваивание.
- Порядок строк не важен: вычислитель строит граф зависимостей.
- Комментарии — `//`.
- В своём скрипте параметры пишутся коротко: `x`, `y`, `rotation`, `sizeY`, `visible`.
- Чужой объект — по `id`: `torso.y`, `head.rotation`, `arm_group.x`.
- `parent` и `inherit` доступны только при наличии родителя; `offset` — тоже.
- Присваивать можно только свои параметры и глобальные переменные.
- Читать можно свои параметры, глобальные переменные, входы, сигналы, `parent`, `inherit`, `offset` и параметры других объектов.
- Инспектор не хранит вторую копию формул: поля редактируют строки скрипта.
- Глобальные переменные вычисляются до объектов и не могут ссылаться на спрайты.

> Почему так: один источник истины и запрет на запись в чужие объекты делают поведение предсказуемым и упрощают диагностику.

## 7. Язык выражений

Поддерживается:

- числа: `1`, `-2.5`, `.5`;
- `+ - * / % ^`;
- сравнения `< <= > >= == !=`;
- логика `and`, `or`, `not` (результат 0/1);
- тернарный оператор `условие ? да : нет`;
- скобки;
- комментарии `//`.

Векторы:

```text
vec(1, 2)
offset.x
orbit(offset, parent.rotation).x
follow(offset, parent).y
pxv(vec(0.5, 1), vec(width, height))
```

Правила:

- `^` — степень, правоассоциативная.
- `%` — остаток.
- Вектор нельзя присвоить числовому параметру. Векторные выражения используются внутри формул и через `.x`/`.y`.
- `.x` и `.y` — доступ к компоненте вектора, а не создание объекта.
- Глобальные переменные — только числа.
- `parent` — не вектор, а пространство имён родителя.
- `offset` — вектор в пикселях только у объекта с родителем.
- `inherit` — число, только у объекта с родителем.
- `width`, `height`, `canvasWidth`, `canvasHeight` — числа в пикселях, только чтение.
- Все векторные функции работают в пикселях сцены; UV переводится через `pxv`/`uvv`.

Никакого `eval` и JavaScript. Собственный парсер, AST и вычислитель.

> Почему так: свой DSL безопасен, даёт понятные ошибки и не зависит от браузерного окружения.

| `uv(value, size)` | px -> UV по одной оси |
| `pxv(v, sizeVec)` | UV-вектор -> px-вектор |
| `uvv(v, sizeVec)` | px-вектор -> UV-вектор |

`follow` использует `parent.sizeX`, `parent.sizeY` и `parent.rotation`. Это основной способ вращать позицию ребёнка вокруг пивота родителя. `rotate` и `orbit` доступны для ручных формул.

Единицы: все векторы в формулах — пиксели сцены. `vlen` на UV-значениях даст бессмысленный результат при неквадратном спрайте; сначала переведите UV в px через `pxv`. `vnorm` возвращает направление без единиц, его можно умножать на пиксельную длину.

### Физика и сглаживание

| Функция | Смысл |
|---|---|
| `smooth(target, halflifeMs)` | экспоненциально догоняет target; за `halflifeMs` проходит половину пути |
| `spring(target, frequencyHz, damping)` | пружина; `damping` 0..1 |
| `inertia(target, accel, friction)` | позже, если `spring` не хватит |

`spring`, `smooth` и `autoblink` — stateful. Ключ состояния: объект или глобальная переменная + параметр/имя + индекс вызова + хеш выражения. При изменении формулы или загрузке пресета состояние сбрасывается. Смена лимита FPS сама по себе состояние не сбрасывает. `dt` ограничивается сверху 50 мс. Физика кадронезависима.

### Случайность

| Функция | Смысл |
|---|---|
| `rnd(seed, min, max)` | детерминированное число из seed |
| `noise(seed, frequencyHz)` | плавный шум -1..1 |
| `shake(amplitude, frequencyHz, seed?)` | плавное дрожание вокруг нуля |
| `random(min, max)` | новое число каждый кадр; использовать редко |
| `autoblink(minMs, maxMs, seed?)` | 0/1; stateful-планировщик моргания |

`rnd` при одном seed всегда даёт одно и то же. `shake` без seed берёт его из объекта, параметра и индекса вызова, чтобы руки не дрожали синхронно.

`autoblink` — обычная stateful-функция для глобальной переменной `blink`. Она сама выбирает интервал и держит импульс. Ручной тест в редакторе — временное переопределение значения `blink` в превью, а не отдельный вход. Если заменить `blink` другой формулой, `autoblink` просто перестаёт использоваться.

## 9. Входы и глобальные переменные

### Входы

Встроенных имён вроде `speak` или `viseme_a` больше нет: **все входы приходят из модулей**.
Экземпляр модуля имеет имя, а его входы адресуются как `<имя>.<вход>`:

| Вход | Значение |
|---|---|
| `time` | секунды с запуска |
| `dt` | секунды с прошлого кадра |
| `<модуль>.<вход>` | значение входа экземпляра модуля, например `mic.talking` или `mic_left.db` |
| `signal.<имя>` | свободный сигнал плагина или внешнего источника |
| `width`, `height`, `canvasWidth`, `canvasHeight` | пиксели (раздел 4.1) |

Имена модулей задаёт пользователь: латиница, цифры и `_`. Один тип можно добавить
несколько раз — два `Loudness` с разными микрофонами дают `mic_left.*` и `mic_right.*`.
Ядро не знает имён заранее: оно получает словарь `values` (ключи `<модуль>.<вход>`) и
резолвит `имя.поле` как вход, если такого ключа нет в обычных полях (`.x`, `.y`, параметры).
Набор модулей хранится в пресете, поэтому чужие пресеты открываются без «висящих» входов.

Шаблоны модулей лежат в `public/modules/*.json` (`index.json` перечисляет файлы): JSON
задаёт входы и поля настроек, а поведение выбирает поле `kind` — `loudness`, `autoblink`,
`manual`, `viseme`. Поэтому новый шаблон добавляется файлом, без правки компонентов:
панель рисует настройки из дескриптора `fields`.

Встроенные шаблоны: **Loudness** (`speak`, `loudness`, `db`, `talking`; источник — микрофон
или отладочный ползунок), **AutoBlink** (`blink` по таймеру), **Manual** (`value`: 0/1 или
число с границами), **Viseme** — похожесть звука на звук. Каждый вход можно выключить
по отдельности: выключенный вход не считается и не попадает в словарь `values`.
Поддержка описана в `docs/MODULES.md`.

Виземы — исключение из «входы из JSON»: у экземпляра свой **список звуков** в настройках
(`config.visemes`) вместе с эталонными спектрами, поэтому входы визем-модуля задаёт не
шаблон, а пресет. Эталоны записываются кнопкой-микрофончиком: 3 секунды, живой спектр,
сохраняется среднее; вариантов записи у одной виземы может быть сколько угодно.
Значение = (`cos²` центрированного в дБ спектра, максимум по вариантам) в степени
«контраста» × гейт громкости, то есть 0…1 — «насколько звук похож на визему»; гейт закрыт
в тишине. «Нормализовать итог» (по умолчанию
включено) делит значения на сумму, чтобы морфинг не выходил за границы. Подпись звука
может быть любой (`ö`, `ы`), имя входа — только латиница: `ö` → `o_umlaut`, `ы` → `y`.

### Глобальные переменные

`globals` — отдельный скрипт. По умолчанию:

```text
blink = auto.blink
breath = sin(time * 2 * pi / 4) * 0.5 + 0.5
```

`blink` — единственный источник истины для моргания: значение приходит из модуля
**AutoBlink**, где интервал, длительность и разброс настраиваются в панели модулей.
Функция ядра `autoblink(min, max)` осталась для ручных скриптов, но в модели рига её
не используем.

`breath` — обычная переменная: частоту, фазу и форму можно менять любой формулой.

Глобальные переменные:

- вычисляются до объектов;
- видят входы, константы и другие глобальные переменные;
- не видят спрайты;
- доступны всем объектам по имени.

> Почему так: глобальные переменные без доступа к спрайтам не создают скрытых циклов и позволяют настраивать дыхание и моргание как обычные формулы.

### Микрофоны и сигналы

Звуком владеют модули, а не панель: у каждого экземпляра `Loudness` свой микрофон
(`deviceId`), усиление и порог речи. Несколько экземпляров открывают разные устройства
независимо, а один и тот же микрофон используется совместно — поток не дублируется.
`AudioContext` создаётся и «пробуждается» из обработчика клика: иначе браузер и WebView2
оставляют его в `suspended` и анализатор молча возвращает нули.

Моргание приходит из модуля `Manual` (`manual.blink`), а `autoblink()` остаётся функцией
ядра для автоматики. Плагины пишут свободные сигналы:

```ts
api.setSignal("viseme_o", 0.7);   // видно как signal.viseme_o
```

В MVP плагины можно не подключать: достаточно модулей и ползунков в редакторе. Архитектура
сигналов остаётся, чтобы позже добавить липсинк без переделки рендера.

## 10. Кадр, зависимости, FPS и защита

### 10.1 Порядок обработанного кадра

Кадр выполняется только когда он разрешён ограничителем FPS:

1. Прочитать монотонные часы и определить фактические `time` и `dt`.
2. Обновить аудио и сигналы из независимых источников.
3. Вычислить глобальные переменные в топологическом порядке, включая `blink` и `breath`.
4. Вычислить параметры объектов в топологическом порядке.
5. Выполнить санитизацию: `NaN`/`Infinity`, ограничения, видимость.
6. Подготовить плоский кадр и порядок отрисовки по `layer`.
7. Отрисовать активное превью и/или оверлей.
8. Отправлять подробную диагностику в панель не чаще 10 Гц.

Пропущенный планировщиком вызов `requestAnimationFrame` не выполняет шаги 1–6 и не создаёт IPC-запрос.

### 10.2 Явный ограничитель частоты кадров

Ограничитель — обязательная видимая настройка, а не скрытая константа.

В панели, рядом с управлением оверлеем и предпросмотром, есть:

- переключатель режима **«Ограниченный» / «По частоте экрана»**;
- числовое поле **«Лимит FPS»**;
- быстрые значения `15`, `24`, `30`, `60`, `120`, `144`, `240`;
- текущий фактический FPS и, в расширенной диагностике, время кадра и число пропущенных/опоздавших кадров.

Правила:

- По умолчанию: `fpsMode = "limited"`, `fpsLimit = 60`.
- В ограниченном режиме допустимы только целые значения `1..240`. Некорректный ввод не попадает в runtime.
- «По частоте экрана» использует `requestAnimationFrame` видимого окна и не означает busy-loop или отключение синхронизации с дисплеем.
- Лимит применяется через монотонные timestamps. `setInterval` как основной кадровый планировщик не используется.
- При опоздании не выполняется серия «догоняющих» кадров. Пропущенные слоты отбрасываются, следующий кадр планируется от текущего времени.
- Изменение лимита применяется без перезагрузки пресета и сброса stateful-формул. Сбрасываются только служебные timestamps планировщика.
- Один и тот же лимит управляет оверлеем и превью панели. Они не запускают две независимые симуляции.
- Аудиозахват и приём сигналов не ограничиваются этим FPS.

### 10.3 Время и низкий FPS

- `time` — активное время рига в секундах, накопленное по монотонным часам, а не `номерКадра / fps`. На паузе оно не продвигается; служебное реальное время продолжает идти, но в это значение не попадает.
- `dt` — фактическое время между **обработанными** кадрами. При лимите 30 FPS типичный `dt` около `1/30`, а не `1/60`.
- Для stateful-физики используется `min(dt, 0.05)`. Реальное `time` не обрезается.
- После сна ПК, паузы или долгой блокировки не проигрываются все пропущенные итерации. Выполняется один кадр с ограниченным physics-`dt` и диагностической отметкой при необходимости.
- `smooth`, `spring`, `noise`, `autoblink` и другие временные функции обязаны сохранять сопоставимую скорость при 30, 60 и 120 FPS.
- `random(min, max)` вызывается не чаще одного раза на обработанный кадр для каждого своего ключа состояния.

### 10.4 Зависимости

- `inherit` и `parent.<param>` зависят от родителя.
- `follow(offset, parent)` зависит от `parent.sizeX`, `parent.sizeY`, `parent.rotation`.
- `offset` статичен для текущей базовой позы.
- Порядок строк в скрипте не влияет на результат.
- AST, граф и планы вычисления перестраиваются только при изменении скриптов, объектов или иерархии, не каждый кадр.

### 10.5 Циклы и защита

Циклы:

- цикл в графе параметров подсвечивается в редакторе;
- параметры из цикла берут значения с прошлого кадра;
- остальная сцена продолжает работать;
- циклы родителей в дереве запрещены на уровне редактора и проверяются при загрузке.

Защита:

- `NaN` и `Infinity` заменяются на последнее валидное значение или безопасное нейтральное значение;
- ограничение количества объектов — 256;
- ограничиваются глубина AST, длина скрипта, число аргументов и сложность одного выражения;
- существует бюджет вычисления кадра; при превышении используются прошлые валидные значения и создаётся диагностика;
- physics-`dt` не больше 50 мс;
- в Canvas никогда не передаются нефинитные координаты, размеры или прозрачность.

> Почему так: явный лимит делает нагрузку управляемой, а фактический `dt` не даёт анимации замедляться вместе с FPS. Ошибка пользователя должна оставаться локальной и не ронять всё приложение.

## 11. Рендер

Canvas 2D в WebView2 — базовый рендер первой версии. Холст масштабируется под `devicePixelRatio`; внутренние координаты сцены при этом остаются в пикселях пресета.

Порядок отрисовки:

1. Отсортировать объекты по `layer` по возрастанию.
2. При равном `layer` — по порядку в массиве `objects`.
3. Группы пропустить.
4. Спрайты с `visible = 0`, `opacity = 0` или нулевым размером пропустить.
5. Отрисовать спрайт.

Трансформация одного спрайта:

```text
pivotPx = vec(pivot.x * width, pivot.y * height)
translate(base.x + x, base.y + y)
rotate((base.rotation + rotation) * pi / 180)
transform(1, tan((base.skewY + skewY) * pi / 180), tan((base.skewX + skewX) * pi / 180), 1, 0, 0)
scale(base.sizeX * sizeX, base.sizeY * sizeY)
drawImage(image, -pivotPx.x, -pivotPx.y, width, height)
```

- `pivotPx` кешируется и пересчитывается при загрузке/замене картинки или изменении `pivot`, но не на каждом кадре.
- Порядок `translate → rotate → skew → scale` даёт предсказуемое вращение вокруг пивота.
- Отрицательный масштаб зеркалит спрайт вокруг пивота.
- Пивот может быть вне картинки.
- `globalAlpha = limit(base.opacity * opacity, 0, 1)`.
- Картинки кешируются; для оффскрина можно добавить culling.
- Прозрачный фон; окно оверлея прозрачное.

> Почему так: Canvas 2D достаточно для PNG-спрайтов, не требует WebGL и легко переносится в превью панели.

## 12. Редактор

Рабочая область состоит из трёх основных зон и дополнительной панели диагностики. Раскладка не является частью пресета.

### 12.1 Настраиваемая ширина и высота панелей

Пользователь может изменить компоновку мышью и точными числовыми значениями:

- вертикальный разделитель между деревом и центральной зоной меняет `leftWidth`;
- вертикальный разделитель между центральной зоной и скриптом меняет `rightWidth`;
- горизонтальный разделитель меняет высоту сцены и инспектора (`sceneHeight`/`inspectorHeight`);
- горизонтальный разделитель над консолью/диагностикой меняет `diagnosticsHeight`;
- правая зона отдаёт скрипту всю высоту: разделителя над редактором нет, а список значений кадра — сворачиваемая полоса внизу (по умолчанию свёрнута, диагностика видна всегда);
- в настройках «Интерфейс → Размеры панелей» те же размеры можно ввести числом в пикселях либо восстановить по умолчанию.

Обязательное поведение разделителей:

- ширина видимой линии может быть 1–2 px, но область захвата — не меньше 6 px;
- используется Pointer Events и pointer capture, чтобы перетаскивание не терялось за пределами линии;
- во время drag отключено выделение текста и случайный drag изображений;
- двойной клик по разделителю возвращает соответствующий размер по умолчанию;
- кнопки позволяют свернуть левую панель, скрипт и диагностику; свёрнутую панель можно вернуть без потери прежнего размера;
- сфокусированный разделитель управляется стрелками: шаг 8 px, с `Shift` — 32 px;
- минимальные размеры защищают содержимое, а центральной сцене всегда остаётся пригодная для работы область;
- при уменьшении окна размеры ограничиваются доступным пространством, а при увеличении не выходят за разумные максимумы;
- изменения применяются без перезапуска runtime и без перезагрузки изображений;
- во время движения мыши обновляются только CSS-размеры через `requestAnimationFrame`; сохранение в сессию выполняется с debounce и на `pointerup`, а не на каждый `pointermove`.

Стартовые ориентиры для большого окна: дерево `260 px`, скрипт `460–520 px`, диагностика `160–200 px`. Это значения по умолчанию, а не жёсткие ограничения. Конкретные минимумы определяются на реальных размерах окна и масштабе интерфейса.

Команда **«Сбросить раскладку»** восстанавливает всю компоновку отдельно от настроек пресета.

### 12.2 Слева — дерево объектов

- Спрайты и группы с миниатюрами.
- Иерархия с drag&drop: смена родителя и порядка.
- `parentId` скрыт от пользователя и меняется только деревом; поле нельзя ввести вручную.
- Перетаскивание в собственного потомка запрещено, поэтому цикл нельзя создать через интерфейс.
- Создание группы из выделения.
- Импорт, дублирование, удаление, переименование.
- Переименование `id` выполняется как рефакторинг: обновляет `parentId` и ссылки в скриптах. Изменение только отображаемого `name` ссылки не трогает.
- Слои и быстрый доступ к видимости.
- Двойной клик открывает скрипт объекта.

### 12.3 По центру — сцена и инспектор

Сцена — интерактивное превью с зумом и панорамированием. Размер её области управляется разделителями из раздела 12.1.

Общие возможности:

- Размер холста (`canvas.width/height`) правится прямо в сцене: клик по подписи
  «ширина × высота» в левом верхнем углу артборда открывает поле, `Enter` применяет,
  `Escape` отменяет. Значение пишется в пресет через `commit`, то есть попадает в Undo;
  мусор и размеры вне 16…16384 px отбрасываются. Отдельного поля в инспекторе нет.
- Импорт пачки картинок ставит **все** спрайты в центр холста: каскадного сдвига на
  28 px больше нет, иначе файлы уезжали по диагонали за пределы артборда.
- `Delete` и `Backspace` удаляют выделение (в полях ввода и в редакторе скрипта — нет).
- Выбранный объект имеет рамку и маркер пивота.
- Клик по спрайту выбирает его; при пересечении объектов сначала выбирается верхний по порядку отрисовки.
- Инструменты: выделение/перемещение, пивот, панорамирование; позже — вращение и масштаб.
- Режимы «показать пивоты», «показать границы», сетка и привязка.
- Колесо меняет зум относительно курсора; `Space` + drag или средняя кнопка панорамирует сцену.
- Инспектор — оверлей или отдельная секция поверх/под сценой: картинка, слой, видимость, прозрачность, базовая поза, пивот, быстрые поля формул.
- Шаг стрелок у числовых полей вводится руками: справа от кнопок `−`/`+` стоит чип с текущим
  шагом (например, `1°` для поворота или `5` для позиции). Клик по чипу открывает поле ввода,
  `Enter` применяет, `Escape` отменяет. Шаг запоминается в `localStorage` по подписи поля, то есть
  действует для всех объектов сразу. Значение по умолчанию у поворота — `1°`: доводить угол по
  `0.1°` сотнями кликов бессмысленно, точное число проще вписать в само поле.
- `parentId` в инспекторе не редактируется вручную; допустимы только безопасные операции дерева.
- Поля формул редактируют строки скрипта, а не отдельную копию.
- Есть кнопка «перейти к строке в скрипте».

#### Прямое перетаскивание спрайта по сцене

Перемещение мышью — равноправный способ редактирования наряду с числовыми `base.x/base.y` в инспекторе:

1. В режиме выделения пользователь зажимает левую кнопку на спрайте и тащит его.
2. Дельта указателя переводится из экранных координат в координаты сцены с учётом зума и панорамирования.
3. Эта дельта добавляется к `base.x/base.y`. Динамические `x/y` из скрипта не перезаписываются, не обнуляются и продолжают добавляться к базе.
4. Поля инспектора обновляются синхронно; после отпускания кнопки весь drag сохраняется как **одно** действие Undo.
5. Изменение базовой позы родителя перемещает базовые позы его потомков на ту же дельту, сохраняя их `offset`. Родитель и соседи выбранного объекта не двигаются.
6. Перетаскивание группы аналогично двигает всё её поддерево.
7. `Shift` временно ограничивает движение доминантной осью; `Alt` временно отключает привязку. Стрелки сдвигают выделение на 1 px, с `Shift` — на 10 px.
8. Автопрокрутка/панорамирование у края не должно менять масштаб или создавать скачок координат.

Во время drag нельзя вычислять новую базу из абсолютной экранной позиции мыши без поправки на зум и исходную точку захвата: это дало бы скачок. Используется именно дельта от начала жеста.

Если объект анимирован, drag всё равно меняет только базу. Для точной настройки пользователь может поставить превью на паузу; это не обязательное условие перемещения.

Клик в режиме пивота не перемещает объект:

- у спрайта он задаёт UV-пивот с последующим переводом в пиксели для геометрии;
- у группы настоящим пивотом остаётся `base.x/base.y`, а UV-подобное значение служит только для отображения.

При редактировании базовой позы родителя его потомки изменяются вместе с ним: перенос, поворот и масштаб применяются к их `base`. Это операция редактора, не рантайма.

### 12.4 Справа — скрипт

CodeMirror 6:

- подсветка синтаксиса, номера строк; в заголовке `on mouse.left.down` модуль и вход подсвечены как
  свойства, тип (`down`, `up`, `change`, `hold`, `relax`) — отдельным цветом;
- автодополнение объектов, параметров, функций, входов, глобальных переменных; у функции в
  списке видна сигнатура (`spring(target, frequencyHz, damping)`) и короткое описание;
- подсказка по аргументам: курсор внутри вызова показывает подпись функции и текущий аргумент,
  а под редактором лежит список всех функций с сигнатурами (клик вставляет вызов);
- диагностика: неизвестные имена, арность, циклы, `parent`/`offset` без родителя;
- панель ошибок с переходом на строку;
- список глобальных переменных и входов с текущими значениями;
- шпаргалка по функциям;
- вкладки «Поведение» (пресет ползунков, см. §5.6), «Объект», «Глобальные», «Входы», «Модули»;
  «Поведение» стоит левее «Объекта», потому что новичок начинает с него, а код открывает вторым;
- авто-применение с debounce или кнопка «Применить»;
- ширина всей зоны и высота вспомогательных списков настраиваются пользователем.

Изменение размера панели не должно заново создавать EditorView или терять историю Undo, позицию курсора и выделение.

### 12.5 Отладка

- текущие динамические значения выбранного объекта;
- значения входов и глобальных переменных;
- входы модулей с их полными именами (`mic.talking`, `viseme.a`) и ползунки ручных модулей;
- кнопка «моргнуть»;
- пауза и покадровый шаг;
- фактический FPS, время вычисления, время рендера и опоздавшие кадры;
- предупреждения о дробном `visible`, ошибках и превышении бюджета.

Пауза останавливает продвижение времени рига, но не блокирует интерфейс и изменение базовой позы. Покадровый шаг выполняет ровно один вычислительный кадр с явно заданным тестовым `dt`.

### 12.6 Интерфейс

Спокойная серая палитра, меньше насыщенных акцентов. Сцена и скрипт не конкурируют за место: пользователь сам распределяет ширину и высоту. Размеры, зум, панорамирование и свёрнутость панелей восстанавливаются после перезапуска.

> Почему так: инспектор не должен быть вторым источником данных, а прямое манипулирование сценой и настраиваемая раскладка сокращают постоянные переключения между полями, деревом и скриптом.

## 13. Rust runtime, панель и оверлей

### 13.1 Ответственность компонентов

**Rust runtime — «мозг»:**

- монотонные часы и продвижение кадра;
- вычислитель DSL и глобальные переменные;
- граф зависимостей и состояние stateful-функций;
- санитизация и подготовка готового кадра;
- пресет, ассеты и нативные операции;
- в конечной архитектуре — аудиозахват и расчёт аудиосигналов.

**Панель на React — управление и настройка:**

- дерево, сцена редактирования, инспектор, скрипт;
- выбор микрофона и отображение аудиовходов;
- настройка FPS, оверлея и интерфейса;
- превью готовых кадров;
- диагностика и сообщения об ошибках.

**Оверлей — «экран»:**

- прозрачное Windows-окно для OBS;
- `requestAnimationFrame` и локальное отсечение кадров выше заданного лимита;
- запрос готового кадра у Rust;
- отрисовка спрайтов без вычисления формул;
- команды размера, прозрачности, click-through и скрытия приходят из панели.

Панель не является обязательным покадровым таймером. Её скрытие не должно влиять на оверлей.

### 13.2 Протокол

Логические сообщения:

- `rig_scene` — статичные объекты, ссылки на декодированные картинки, пивоты, базы, порядок и версия сцены; обновляется только при соответствующих изменениях;
- `rig_tick` — запрос активного драйвера на продвижение и получение следующего готового кадра;
- `rig_latest_frame` — получение последнего готового кадра без продвижения симуляции;
- `rig_diagnostics` — агрегированные метрики и ошибки, обычно не чаще 10 Гц;
- команды редактора и окна — отдельные нечастые операции, не входящие в горячий путь.

Статическая сцена не пересылается каждый кадр. В кадре передаются только необходимые динамические значения и служебные номера версии/кадра. Изображения не пересылаются в `rig_tick`.

Для горячего пути предпочтителен плоский заранее выделенный буфер без создания сотни строк и объектов на кадр. JSON допустим на раннем прототипе для проверки корректности; окончательный транспорт выбирается замером и не меняет семантику протокола.

### 13.3 Единый источник продвижения

Панель и оверлей не имеют права независимо продвигать одну и ту же симуляцию:

1. Если оверлей открыт и активен, он — основной драйвер `rig_tick`.
2. Превью панели в это время использует `rig_latest_frame` или получает готовые кадры, не вызывая новый шаг.
3. Если оверлея нет, активным драйвером становится видимое превью панели.
4. Переключение драйвера выполняется через Rust и не создаёт двойной шаг за один слот.
5. Даже при одновременных запросах runtime возвращает один согласованный номер кадра и не выполняет stateful-функции дважды.

Если ни одно превью не требуется, runtime может не вычислять новые визуальные кадры. При возобновлении не выполняется накопленная очередь шагов.

### 13.4 План при проблемах производительности

Сначала измеряются вычисление, сериализация, IPC и рисование по отдельности. Если pull-запросы не удерживают кадровый бюджет:

1. уменьшить объём передаваемых данных и убрать аллокации;
2. перейти на компактный бинарный кадр;
3. вынести планировщик в Rust и оставить в окнах только получение последнего готового кадра;
4. рассмотреть общий буфер или иной нативный транспорт;
5. только после профилирования рендера решать, нужен ли выход за пределы Canvas 2D.

Эти изменения не затрагивают DSL, модель объектов или формат пресета.

> Почему так: Rust с самого начала убирает зависимость вычислений от фонового WebView, а единый драйвер исключает удвоение времени и состояния при одновременно открытых панели и оверлее.

### 13.5 Состояние реализации оверлея (0.1)

Реализовано:

- страница `overlay.html` (второй entry Vite) — прозрачный документ без интерфейса; служебная рамка включается параметром `guide=1`;
- общий с редактором Canvas 2D-рендер (`src/render/rigCanvas.ts`): один код отрисовки, один внешний вид;
- протокол `hello → announce → scene → pose/config → frame`; сцена и изображения пересылаются один раз, затем идут только патчи базовой позы, конфигурации и готовые кадры;
- три транспорта: `BroadcastChannel` (одно окно браузера или второго окна), события Tauri (нативные webview) и необязательный WebSocket-мост для источника браузера в OBS; кадры дедуплицируются по `seq`;
- настройки оверлея в пресете (`OverlayConfig`): размер окна, вписывание, фон/хромакей, `always-on-top`, click-through, служебная рамка;
- окно Tauri создаётся прозрачным, без декораций, тени и значка на панели задач, с применением флагов на лету.

Осталось до полного соответствия §13:

1. `rig_tick`/`rig_latest_frame` и планировщик в Rust, чтобы оверлей был главным драйвером, а скрытая панель не влияла на поток кадров; сейчас драйвером остаётся окно редактора без двойного продвижения.
2. Встроенный в приложение сервер вместо внешнего `scripts/overlay-bridge.mjs`.
3. Проверка прозрачности и захвата OBS на реальной Windows-машине; выбор официально рекомендуемого способа захвата.

> Почему перенесено: подготовка кадров уже отделена от отрисовки, поэтому перенос планировщика в Rust не меняет ни DSL, ни формат пресета, ни протокол оверлея.

## 14. Группы, формат и правила

### Группы

- Группа — объект без картинки, но с `base`, `layer` и скриптом. Её настоящий пивот — `base.x/base.y`; UV-доля `pivot` вычисляется из границ только для интерфейса.
- Границы группы — объединение базовых границ детей; для группы с вложенными группами — рекурсивно.
- При изменении границ `base.x/base.y` не двигается: группа продолжает вращаться вокруг своей точки, а UV-доля пересчитывается для отображения.
- Группа не рисуется, но её динамические `layer`, `opacity` и `visible` наследуются детьми по умолчанию (через `inherit`).
- Вложенность групп разрешена. Циклы невозможно создать через дерево; загрузчик всё равно проверяет данные на циклы.
- Перетаскивание группы двигает всё поддерево.
- Поворот и масштаб базовой позы группы применяются к потомкам сразу, как операция редактора.
- При создании группы из выделения её `base` ставится в центр общих границ, дети получают `parentId` группы.

### Родитель, удаление, переименование

- При удалении родителя дети переходят к родителю удалённого объекта.
- Если родителя нет, дети становятся корневыми.
- Ссылки на удалённый `id` в скриптах заменяются на нового родителя.
- Переименование `id` обновляет `parentId` и все ссылки в скриптах.
- `parentId` не редактируется вручную; дерево не даёт выбрать самого себя или потомка. Загрузчик дополнительно отклоняет циклы в повреждённом файле.

### Формат

- Только `version: 2`. Старые пресеты не конвертируются и не удаляются; показываются как несовместимые.
- `objects` хранит порядок в структуре: он же tie-break для слоёв (см. «Порядок отрисовки»).
- Ассеты лежат в данных приложения; в пресете хранятся относительные пути.
- Сессия хранит текущий пресет, настройки окна, зум/панорамирование сцены и все размеры панелей из `EditorLayout`.
- Изменение раскладки сохраняется независимо и не вызывает автосохранение пресета.
- Автосохранение с debounce; явное сохранение тоже доступно.
- Кадровая анимация внутри спрайта в v2 отсутствует. Позже её можно сделать плагином: группа из нескольких спрайтов, плагин переключает `visible` по времени или случайно.

### Правила значений

- Пивот может выходить за 0..1.
- Отрицательный `size` зеркалит.
- `visible` — 0/1; дробное значение округляется с предупреждением.
- `layer` — число; дети по умолчанию наследуют слой родителя.
- `opacity` — множитель; итог ограничивается 0..1.
- `base.opacity` и `base.visible` — статичные значения по умолчанию; скрипт может их переопределить.

> Почему так: абсолютные базовые позы и явные формулы проще отлаживать, а операции с группой остаются предсказуемыми.

## 15. Производительность и оптимизация

Размер приложения не ограничивает архитектуру, но производительность и отсутствие утечек являются обязательными требованиями.

### 15.1 Горячий путь

- Парсинг и построение AST выполняются при изменении скрипта, не при вычислении кадра.
- Доступ к параметрам в скомпилированном плане идёт по числовым индексам, а не по строковым именам.
- Граф зависимостей и топологический план кешируются.
- Буферы текущего и предыдущего кадра переиспользуются; цель устойчивого состояния — отсутствие массовых аллокаций на каждом кадре.
- Диагностические строки формируются только при ошибке или по таймеру публикации, а не для каждого параметра каждого кадра.
- При пропущенном FPS-планировщиком кадре не выполняются вычисления и IPC.
- Картинки загружаются и декодируются один раз, кешируются и не пересылаются между окнами каждый кадр.
- При смене пресета неиспользуемые ассеты и буферы освобождаются; размер установщика не является оправданием утечек памяти.
- Редактор не обновляет React-дерево с частотой кадра: покадровые значения идут в Canvas и ограниченные по частоте диагностические представления.

### 15.2 Измерения

Профилируются раздельно:

1. обновление аудио и сигналов;
2. вычисление глобальных переменных;
3. вычисление объектов;
4. сериализация и IPC;
5. сортировка и подготовка draw list;
6. Canvas-рисование;
7. работа редактора и пересохранение сессии.

Метрики: среднее, p95 и p99 времени, фактический FPS, опоздавшие кадры, число аллокаций/объём памяти при длительном прогоне. Оптимизация выполняется по профилю, а не по предположению.

Предварительная цель прототипа: 200 простых спрайтов при 60 FPS и запас по времени вычисления. Она становится приёмочной только после выбора эталонного ПК и тестового пресета. Дополнительно проверяются 30/60/120 FPS и длительная работа не меньше часа.

### 15.3 Что не оптимизируем преждевременно

- Не добавляем WebGL/wgpu или собственный нативный рендер, пока Canvas 2D не доказал свою недостаточность на согласованном сценарии.
- Не усложняем DSL JIT-компиляцией на первом этапе; сначала компактный AST/план и интерпретатор без лишних аллокаций.
- Не экономим на безопасности скриптов, проверках границ и понятной диагностике ради микрооптимизаций.

## 16. Этапы реализации

0. **Короткие технические прототипы Windows**: прозрачное Tauri-окно и захват в OBS, click-through, доступ к ассетам, Canvas 2D со 100–200 спрайтами, скрытая панель, базовый `rig_tick`. Риски фиксируются до большого объёма UI.
1. **Ядро языка на Rust**: лексер, парсер, AST, вычислитель, математика, векторы, `rotate`/`orbit`/`follow`, unit-тесты. Без UI.
2. **Модель и runtime**: объекты, `parentId`, `inherit`, `offset`, топологический порядок, attach/detach, циклы, защита, stateful-состояние, монотонные часы и ограничитель FPS.
3. **Рендер**: спрайты, пивоты, слои, базовая поза, отрицательный размер, прозрачность, подготовка плоского кадра.
4. **Редактор**: дерево, сцена, инспектор, группы; настраиваемая ширина/высота панелей; прямое перетаскивание спрайтов; Undo; базовые трансформации поддерева.
5. **Скрипт-редактор**: CodeMirror 6, диагностика, автодополнение, глобальные переменные, тестовые входы; сохранение состояния при изменении размеров панели.
6. **Панель и оверлей**: прозрачное окно, протокол сцены и кадров, UI настроек оверлея и ограничителя FPS — сделано в 0.1; осталось перенести планировщик (`rig_tick`, `rig_latest_frame`) в Rust и проверить скрытую панель.
7. **Аудио**: микрофон, `speak`, `loudness`, `db`, `talking`, глобальные `blink`/`breath`, `autoblink`; проверка независимой работы аудиопотока.
8. **Серый UI**: окончательная палитра, компоновка, состояния панелей, доступность разделителей.
9. **Пресеты, сессия, ассеты, импорт/экспорт**: миграции только при появлении следующей версии формата, автосохранение и восстановление.
10. **Плагины и сигналы**, затем кадровая анимация плагином.

Три дополнительных требования не откладываются на финальную полировку: FPS закладывается в этап 2, а размеры панелей и перемещение по сцене входят в первую версию редактора на этапе 4.

## 17. Тесты и приёмка

### 17.1 Язык и модель

Обязательные:

- приоритет операторов, тернарник, правоассоциативность `^`;
- `clamp(x, ref, lo, hi)`, `limit`, векторные функции и ошибки арности;
- `inherit` равен соответствующему `parent.<param>`;
- `offset` и `follow` при повороте родителя на 90°;
- `follow` при масштабе родителя;
- двухуровневая иерархия: внук следует за поворотом деда;
- `pivot` на спрайте 2:1 переводится в px без искажения; `pxv`/`uvv` обратимы;
- `vlen` на px даёт px, `vnorm` безразмерен;
- отрицательный `size` зеркалит;
- `visible` 0/1 и округление дробного с предупреждением;
- сортировка по `layer` и tie-break;
- attach/detach: нейтральные строки меняются на `inherit`, пользовательские не трогаются;
- удаление родителя и перепривязка ссылок;
- `parentId` не доступен из скрипта и не задаётся вручную;
- цикл параметров берёт прошлый кадр;
- цикл родителей отклоняется загрузчиком;
- `NaN`/`Infinity` не попадают в Canvas;
- `rnd` детерминирован, `shake` не синхронен;
- `autoblink` даёт 0/1 и сбрасывается при смене формулы;
- `spring`/`smooth` стабильны при скачках `dt`;
- глобальные переменные не видят спрайты;
- `blink`/`breath` переопределяются как обычные глобальные переменные;
- `parent`/`offset` без родителя дают диагностику.

### 17.2 Ограничитель FPS

На виртуальных часах, без зависимости от реального времени CI:

- при виртуальном дисплее 144 Гц и лимите 30 обрабатываются только разрешённые кадры, средняя частота близка к 30;
- лимиты 1, 24, 30, 60, 120 и 240 проходят граничные проверки;
- значения 0, отрицательные, дробные, `NaN`, строки и числа выше 240 отклоняются или нормализуются с явным сообщением;
- режим «По частоте экрана» не запускает дополнительный таймер;
- смена 30 → 60 → 144 применяется без перезагрузки и без сброса `spring`, `smooth`, `autoblink`;
- после паузы на несколько секунд нет серии догоняющих кадров;
- `time` соответствует монотонным часам, а `dt` — интервалу между обработанными кадрами;
- скорость `smooth`, `spring`, `noise` и `autoblink` сопоставима при 30/60/120 FPS;
- одновременные запросы панели и оверлея не продвигают stateful-функции дважды;
- пропущенные планировщиком кадры не вызывают `rig_tick`.

Ручная приёмка: лимит виден в основной панели, фактический FPS меняется в соответствии с настройкой, а скорость движения не меняется при переключении 30/60 FPS.

### 17.3 Перетаскивание по сцене

- При зуме 50%, 100% и 200% объект перемещается на ту же сценную дельту, что и указатель с учётом масштаба.
- Панорамирование перед drag не вызывает смещение или скачок в начале жеста.
- Итоговые `base.x/base.y` совпадают с результатом ручного ввода тех же значений в инспекторе.
- Динамический скрипт `x/y` не изменяется.
- Потомки получают ту же базовую дельту, их `offset` сохраняется; родитель и соседи не затрагиваются.
- Отпускание мыши создаёт одну запись Undo; Undo/Redo возвращает всё поддерево согласованно.
- `Shift` ограничивает ось, `Alt` отключает привязку, стрелки дают точный сдвиг.
- Drag не теряется при выходе курсора за Canvas и не выделяет текст интерфейса.
- Режим пивота не перемещает базовую позу.

### 17.4 Размеры панелей

- Можно изменить ширину дерева и скрипта, высоту сцены/инспектора и высоту диагностики.
- Центральная зона не исчезает даже при максимально узком окне; ограничения размеров применяются предсказуемо.
- Размеры сохраняются после перезапуска и не попадают в файл пресета.
- Двойной клик и общая команда сброса восстанавливают размеры.
- Сворачивание/разворачивание возвращает прежний размер.
- CodeMirror не теряет Undo, курсор, выделение и содержимое при resize.
- Сцена корректно пересчитывает Canvas под новый размер и `devicePixelRatio`, не меняя координаты объектов.
- Изменение раскладки не создаёт дополнительных кадров рига и не сбрасывает stateful-состояние.
- Разделители работают мышью, пером и клавиатурой.

### 17.5 Рендер, окна и нагрузка

- 200 спрайтов укладываются в согласованный бюджет на эталонном ПК.
- Скрытая/свёрнутая панель не останавливает оверлей и аудио.
- OBS корректно захватывает прозрачный оверлей выбранным документированным способом.
- Часовой прогон не показывает постоянного роста памяти и постепенного падения FPS.
- Ошибка скрипта или переполнение бюджета не приводит к пустому/повреждённому кадру без диагностики.

## 18. Что проверить прототипами до крупной реализации

- Прозрачность Tauri 2 + WebView2 на поддерживаемых версиях Windows и совместимость с OBS Game Capture/Window Capture. Зафиксировать рекомендуемый способ захвата.
- Click-through и управление окном без мерцания и потери фокуса редактора.
- Не останавливается ли аудиозахват в скрытой панели; если браузерный вариант нестабилен, сразу использовать нативный аудиопоток.
- Успевает ли Rust отвечать на `rig_tick` при 60/120 Гц вместе с сериализацией.
- Не рвётся ли анимация, если панель свёрнута, а оверлей остаётся видимым.
- Хватает ли Canvas 2D на 100–200 реальных PNG/WebP с прозрачностью, масштабом и поворотами.
- Не даёт ли пивот на спрайте 2:1 визуального смещения при повороте и масштабе.
- Как выглядит `skew` через `transform` на реальных картинках.
- Размер CodeMirror 6 учитывается, но не является блокером: приоритет — отзывчивость редактора.
- Загрузка ассетов через asset protocol в оверлее без копирования изображений в каждый кадр.
- Разделители панелей и drag спрайтов при разных `devicePixelRatio` и масштабировании Windows 100%/125%/150%.

## 19. Открытые вопросы, не блокирующие начало ядра

- Конфигурация эталонного ПК для численных performance-бюджетов: CPU, GPU, ОЗУ, частота дисплея.
- Какие микрофоны/драйверы обязательно проверить: обычный USB/аудиовход, виртуальный кабель, ASIO не предполагается без отдельного требования.
- Какой способ захвата OBS становится официально рекомендуемым после прототипа.
- Нужны ли пресетам разные настройки FPS для превью и оверлея. Базовая редакция намеренно использует один лимит и одну симуляцию.
- Точные минимальные размеры панелей после появления реального UI и проверки масштабирования Windows.

Эти вопросы не меняют язык, модель данных и возможность начать этап 1.

## 20. Ближайший шаг

MVP редактора, `rig-core` и прозрачный OBS-оверлей уже созданы в корневой папке `YappyTuberPlus`. Оверлей получает готовые кадры и не продвигает симуляцию дважды; настройки окна, фона и захвата описаны в `docs/OVERLAY.md`. Следующий этап — перенести планировщик кадров в Rust (`rig_tick`/`rig_latest_frame`), чтобы поток в оверлей не зависел от видимости панели, затем нативный Rust-аудиозахват и нагрузочная проверка 100–200 реальных спрайтов на Windows.

Весь дальнейший код, тесты, ассеты и сборочные файлы по-прежнему размещаются только в корневой папке проекта.

## 21. Изменения относительно исходной ревизии 4

- Зафиксированы Windows и стек Tauri 2 + Rust + React/TypeScript.
- Производительность объявлена приоритетом; ограничение на вес приложения снято.
- Rust-вычислитель стал базовой архитектурой, а не запасным вариантом.
- Добавлены настраиваемые ширина и высота панелей, числовой ввод размеров, сохранение раскладки, сворачивание, сброс и клавиатурное управление.
- Прямое перетаскивание спрайтов по сцене детализировано: зум, панорамирование, поддерево, `base`, скриптовая динамика, snapping и Undo.
- Добавлен явный UI ограничителя FPS, диапазон `1..240`, режим по частоте экрана, монотонный планировщик, запрет догоняющих очередей и тесты.
- Разрешён риск двойного продвижения симуляции панелью и оверлеем: есть один активный драйвер и чтение последнего кадра без шага.
