## 0. Как устроено сейчас (для общей картины)

Чтобы дальнейшие правки читались однозначно:

- **Модуль** — экземпляр в пресете: `{ name, type, enabled, source, config }`
  (`src/types.ts`). Тип — `loudness | viseme | manual`, описание типа лежит в
  `src/modules/registry.ts`.
- **Имя модуля** — префикс входа: `mic.talking`, `manual.blink`. Имена
  санитизируются и делаются уникальными (`mic`, `mic_2`, `mic_left`).
- **`source: "live" | "manual"`** — это **одно поле экземпляра**, а не вкладки и
  не отдельные модули. Переключатель «Микрофон / Ползунки» рисуется в карточке
  модуля (вкладка «Модули»), а вкладка «Входы» просто смотрит на то же поле:
  при `live` показывает уровни и дБ, при `manual` — ползунки.
- **Звук** — один `AudioContext` на приложение, отдельный `AnalyserNode` на
  модуль, общий `MediaStream` на устройство (`src/modules/audio.ts`). Два
  Loudness с разных микрофонов работают независимо, с одного — не открывают
  его дважды.
- **Кнопка «Включить микрофоны»** — это не про модули, а про движок звука
  целиком (`useModuleInputs.start/stop`). Она же дублируется во вкладке «Входы».
- **Входы в кадр** — плоский словарь `values` (`composeValues`): у выключенного
  модуля входов нет вовсе. Ядро знает только те имена, что пришли в кадре.

## 1. Правки панели модулей

### 1.1. Тумблер на каждый вход

Сейчас вход показан только как `<code>mic.speak</code>` в подвале карточки, и
отключить его нельзя. Нужен чекбокс/глаз на каждом входе.

Решение: у экземпляра появляется `disabledInputs: string[]` (пусто по
умолчанию — старые пресеты читаются как есть).

Семантика выключенного входа:

- он **не считается** (для `loudness` это значит, что вход не попадает в анализ,
  для ручных — нет ползунка и нет строки во «Входах»);
- он **всё равно уходит в кадр** со значением по умолчанию (`0`, для `db` — `−60`),
  чтобы скрипты, которые его читают, не падали с «неизвестное имя»;
- в карточке он показан приглушённо, с зачёркнутым именем.

Альтернатива (не выбираем без подтверждения): не отправлять вовсе и показывать
диагностику «вход отключён, но используется в скрипте».

### 1.2. Источник модуля: «Микрофон / Ползунок»

Оставляем переключатель (он реально полезен: «работа» ↔ «отладка»), но:

- подписываем явно: **Источник: Микрофон · Ползунок**, и рядом пояснение
  «Ползунок — отладочный режим, значения ставятся вручную»;
- убираем дублирование во вкладке «Входы»: там только бейдж режима, без второй
  пары кнопок;
- `manual` и новый `autoblink` режима «Микрофон» не имеют вообще — у них
  `source` всегда `manual`, переключателя в карточке нет.

### 1.3. `autoblink` вместо `blink` у `manual`

Сейчас `manual` — свалка: единственный вход `blink` со значением 0/1 плюс
кнопка «тестовое моргание» во «Входах». Разделяем:

**Новый тип `autoblink`** (вход `blink`):

- `period` — средний интервал между морганиями, мс (частота);
- `hold` — сколько вход держится в 1, мс (длительность закрытия);
- `jitter` — разброс интервала в процентах, чтобы не было метронома;
- `min` / `max` — в каких пределах гуляет значение (по умолчанию 0…1, чтобы
  можно было отдать и «полуприкрытые глаза»);
- `enabled` — авто-моргание включено (не путать с `enabled` самого модуля).

Считается в рантайме браузера, без изменений ядра: значение входа обновляется
по таймеру и уходит в кадр как обычный вход.

**`manual` становится универсальным ручным входом:**

- один вход (не набор), его имя настраивается в карточке;
- `mode: "flag" | "number"` — тумблер 0/1 или число;
- для `number`: `min`, `max`, `step`;
- `source` всегда `manual`, «автоматом считается вручную регулируемым».

Миграция: у старых пресетов `manual` остаётся с именем входа `blink`, поэтому
существующие скрипты (`manual.blink`) продолжают работать. Новые экземпляры
по умолчанию получают вход `value` → `manual.value`.

### 1.4. Поля настроек — общий дескриптор

Чтобы настраиваемые поля были не только у `autoblink`/`manual`, но и у любых
модулей из библиотеки, в описании типа модуля появляется массив полей:

```ts
interface ModuleField {
  key: string;
  label: string;
  type: "number" | "flag" | "select" | "text";
  min?: number; max?: number; step?: number;
  options?: Array<{ value: string; label: string }>;
  default: number | string | boolean;
  suffix?: string;   // «мс», «дБ», «×»
  hint?: string;
}
```

`ModulesPanel` рисует такие поля автоматически. У `loudness` туда же переезжают
«Усиление», «Порог речи», «Шумоподавление» и выбор устройства — сейчас они
вписаны в компонент руками.

### 1.5. Библиотека модулей вместо «+»

Вместо блока «Добавить модуль» с кнопками по типам:

- сверху — **поле поиска** по уже включённым модулям (по имени, типу и именам
  входов), список фильтруется на месте;
- снизу — кнопка **«Добавить модуль»**, она раскрывает палитру: список доступных
  шаблонов с поиском, клик — добавить, Esc — закрыть.

Откуда берутся шаблоны (локальная папка `modules`):

- в репозитории `public/modules/*.json` + `public/modules/index.json` — их
  отдаёт и dev-сервер, и `.exe` (файлы вшиты в сборку), и автообновление
  приносит новые шаблоны вместе с кодом;
- позже — дополнительная пользовательская папка (`%APPDATA%`), чтобы можно было
  класть свои шаблоны без обновления репозитория.

Формат шаблона (черновик):

```json
{
  "id": "autoblink",
  "title": "AutoBlink",
  "description": "Моргание по таймеру с разбросом интервала.",
  "kind": "autoblink",
  "inputs": [{ "name": "blink", "label": "Моргание", "kind": "flag" }],
  "fields": [
    { "key": "period", "label": "Интервал", "type": "number", "min": 800, "max": 12000, "step": 100, "default": 4200, "suffix": "мс" }
  ],
  "defaults": { "period": 4200, "hold": 140, "jitter": 35, "min": 0, "max": 1 }
}
```

Ограничение, которое надо проговорить: JSON-шаблон сам ничего не считает — он
описывает входы и настройки, а поведение берётся из `kind` (реализовано в коде:
`loudness`, `manual`, `autoblink`, `viseme`). Своя математика в шаблоне — это
следующий шаг (пользовательское выражение/скрипт, исполняемый в песочнице
рантайма), сейчас не делаем.

### 1.6. Убрать глобальную кнопку микрофонов

Кнопка «Включить/выключить микрофоны» уходит из обеих вкладок: она захламляет
панель, если микрофонных модулей в модели нет, и дублирует то, что уже есть у
модуля.

Новое поведение:

- включение `loudness` чекбоксом в карточке = запрос доступа к микрофону
  (клик — валидный жест для `AudioContext`, поэтому `start()` вызывается именно
  из обработчика);
- выключение модуля отцепляет его поток, остальные продолжают работать;
- если микрофонных модулей нет — про звук вообще ничего не показывается;
- ошибки (нет доступа, устройство занято) показываются **внутри карточки
  модуля**, а не общим баннером.

## 2. На будущее: клавиатура, мышь, события

Записано по просьбе, в этой итерации не реализуется.

### 2.1. Модуль `keyboard`

- постоянные входы по нажатым клавишам: `keyboard.e` = 1, пока клавиша нажата
  (отпустили — 0), поэтому объект может читать `keyboard.e` как обычный вход;
- набор клавиш задаётся в настройках модуля (или «любая клавиша» + имя входа
  берётся из конфига);
- несколько модулей `keyboard` можно ставить рядом (`keyboard_2` и т.д.).

### 2.2. Модуль `mouse`

- кнопки: `mouse.left`, `mouse.right`, `mouse.middle` (0/1);
- относительное движение: `mouse.dx`, `mouse.dy` (приращение за кадр);
- абсолютное: `mouse.x`, `mouse.y` (нормированные 0…1 по окну/экрану);
- колесо: `mouse.wheel`.

### 2.3. События

Идея: помимо «значение, пока держится», нужен **разовый запуск кода**.

- `keyboard.e` — постоянный вход (держится, пока нажато);
- `keyboard.event_pressed.e { … }` — вызывается **один раз** в момент нажатия,
  как прерывание;
- `keyboard.event_released.e { … }` — то же на момент отпускания.

Технически это значит: рантайм получает от модуля не только значения, но и
очередь событий; на кадре события снимаются и выполняются один раз, до расчёта
выражений объектов. Блок `{ … }` — тот же язык скриптов, что у объектов
(доступны глобальные переменные, модульные входы, `smooth/spring/follow`).

Для `mouse` аналогично: `mouse.event_pressed.left`, `mouse.event_released.left`.

### 2.4. Переменная-посредник вместо шортката у модуля

Не хотим, чтобы модуль знал про шорткаты: это размазывает логику по настройкам
модулей. Вместо этого:

```
# глобальные
toggle_mic = keyboard.q          # значение нужного модуля
mic_on = toggle_mic > 0.5

# объект читает переменную
... = mic_on ? mic.speak : 0
```

То есть клавиатура/мышь дают входы, глобальные переменные собирают из них
управление, а объекты читают переменные. Шорткат на включение/выключение самого
модуля — тоже через событие:

```
keyboard.event_pressed.q { mic_enabled = 1 - mic_enabled }
```

### 2.5. Ограничения, которые надо учесть при реализации

| Где | Клавиатура/мышь |
|---|---|
| Браузер | только пока окно в фокусе (`keydown`/`keyup`, `mousemove` на window); глобальных хуков нет |
| Нативное окно Tauri | глобальные горячие клавиши — `tauri-plugin-global-shortcut`; мышь и «нажатия вне окна» — отдельный хук (`rdev`/`device_query`), требует разрешений в capabilities |
| Оверлей (click-through) | клавиатуру получает окно редактора, а не оверлей — события должны идти от одного источника и раздаваться всем окнам |

## 3. Порядок работ и что нужно подтвердить

Предлагаемая последовательность (каждый шаг — отдельный коммит и проверка):

1. Дескриптор полей `ModuleField` + отрисовка настроек из него (без новых типов).
2. Тумблеры входов (`disabledInputs`) + поиск по включённым модулям.
3. `autoblink` и переработка `manual` (+ миграция `manual.blink`).
4. Убрать глобальную кнопку микрофонов, включение через модуль.
5. Библиотека шаблонов из `public/modules/` + палитра добавления.
6. Только после этого — `keyboard` / `mouse` / события как отдельный план 0.5.

Открытые вопросы (нужны ответы, чтобы не переделывать):

- отключённый вход: отправлять нулём (скрипты не ломаются) или не отправлять
  вовсе (в диагностике будет видно, что вход используется, но выключен)?
- имя входа у переработанного `manual`: настраиваемое (старые остаются на
  `blink`, новые — `value`) или всегда `value` с миграцией скриптов?
- библиотека: хватает папки `public/modules/` в репозитории или сразу нужна
  пользовательская папка рядом с приложением?
