## 0. Решения, зафиксированные по итогам обсуждения

| Вопрос | Решение |
|---|---|
| Tauri-приложение | вторая фаза; разработка остаётся в браузере, `--app` — по желанию |

## 1. Ответы на прямые вопросы

### Запуск приложением, а не в браузере

Каркас Tauri 2 уже лежит в репозитории (`src-tauri`), окно прописано, `npm run tauri dev`
работает как задумано. Не хватает только окружения на машине:

- Rust (`rustup`, stable) — около 300 МБ;
- MSVC Build Tools — от 2 ГБ (нужны Tauri и `rig-core`);
- WebView2 — в Windows 11 уже есть;
- первая сборка Tauri — 5–15 минут, дальше инкрементально быстро.

Что предлагаю:

1. Добавить в лаунчер режим `--app`: он проверяет Rust/MSVC, предлагает доставить через
   `winget` (`Rustlang.Rustup`, `Microsoft.VisualStudio.2022.BuildTools`), затем запускает
   `npm run tauri dev`.
2. **Разработку оставить в браузере** — HMR мгновенный, правки в Rust-ядре всё равно идут
   через `wasm32`. Приложение запускать для проверки захвата в OBS и «как у пользователя».
3. Установщик (NSIS) — отдельным шагом позже, когда устаканится UI.

**Насколько это замедлит правки.** Почти никак, если браузер остаётся основным циклом:

- код один и тот же, отдельного «нативного» UI нет — Tauri загружает тот же Vite-сервер;
- ежедневная работа: `npm run dev`, HMR как сейчас;
- Tauri нужен только для проверки окон, прозрачности и захвата; запуск по флагу `--app`;
- цена: один раз поставить Rust + MSVC (~2,5 ГБ), первая сборка 5–15 минут, плюс `cargo`
  пересобирается при правках Rust-ядра.

Реальное замедление одно: **проверять сборку отсюда я не могу** (нет Rust и Windows), поэтому
цикл «изменил → проверил» для нативных окон будет идти через вас и лог.

**Рекомендация:** вторая фаза, сразу после UI-правок. Ежедневную скорость разработки не меняет.

### Разница между «Сохранить пресет» и «Экспорт JSON»

Разница есть, и она в месте хранения:

| Кнопка | Что делает |
|---|---|
| Сохранить | пишет в `localStorage`, причём автосохранение уже идёт каждые 700 мс и `Ctrl+S` делает то же самое |
| Экспорт JSON | скачивает файл `.yappy.json` на диск |
| Открыть | читает файл `.yappy.json` |

То есть «Сохранить» дублирует автозейв, а файл — единственный способ сделать бэкап и
перенести пресет. Варианты:

- **A (рекомендую):** две кнопки — «Открыть» и «Сохранить». «Сохранить» скачивает файл,
  локальное автосохранение остаётся автоматическим и показывается в строке состояния
  («Сохранено локально · 14:32»). `Ctrl+S` = сохранить файл.
- **B:** «Сохранить» с маленьким меню: «В приложении» / «Файлом».

**Уточнение по факту:** сейчас пресеты **не файлы**, а строка JSON в `localStorage` браузера.
Кнопка «Экспорт» просто скачивает эту строку файлом, поэтому «Сохранить» и «Экспорт» и
дублируют друг друга.

Предлагаю модель «текущий файл», как вы описали:

| Действие | Браузер (Chrome/Edge) | Приложение (Tauri) |
|---|---|---|
| Сохранить | перезапись текущего файла через File System Access API | запись в папку приложения |
| Сохранить как… (стрелка) | выбор папки и имени через системный диалог | нативный диалог сохранения |
| Автосейв | по-прежнему `localStorage`, чтобы ничего не потерять при падении | то же |
| Открыть | выбор файла | нативный диалог |

В браузере «Сохранить» без выбранного файла один раз спросит папку/имя, дальше перезаписывает
молча — это ровно то поведение, которое вы описали. В Firefox/Safari API нет: там останется
скачивание файла (и это будет единственное отличие). В приложении «папка приложения» —
`%APPDATA%/YappyTuberPlus/presets`, плюс «Сохранить как…» в любую директорию.

Также в строке состояния будет честный индикатор: «изменено · автосохранено 14:32 ·
файл: mochi.yappy.json».

## 2. Найденные причины двух багов

### 2.1 Скрытие панелей ломает раскладку (скриншот)

`src/App.tsx` задаёт сетку из пяти колонок:

```text
[leftWidth] 8 [minmax(300px,1fr)] 8 [rightWidth]
```

а элементы — панель, разделитель, центр, разделитель, панель. Свёрнутая панель скрывается
через `display: none` (`styles.css`, `.left-collapsed .left-workspace`). Скрытый элемент
**выпадает из потока сетки**, и оставшиеся четыре раскладываются по первым четырём
колонкам со сдвигом:

- разделитель попадает в колонку `0px`;
- сцена — в колонку разделителя `8px` (на скриншоте это тонкая вертикальная линия);
- второй разделитель растягивается на `1fr` — то самое большое пустое поле;
- скрипт попадает в `8px`, справа остаётся неиспользованная `rightWidth`.

Отсюда и «на долю кадра деформирует» при скрытии только скрипта: сдвигается на один
элемент, но кадр пересборки сетки виден.

**Исправление:** все пять детей остаются в сетке всегда; каждому явно назначается
`grid-column` (1…5), ширина свёрнутой колонки — `0`, содержимое панели скрывается внутри
обёртки. Плюс `minmax(0, 1fr)` для центра, чтобы min-content не распирал колонку.

### 2.2 Кнопка сетки не работает

`src/components/Scene.tsx`: цикл отрисовки запускается один раз
(`useEffect(..., [])`) и вызывает `draw()` из **первого** рендера. `draw` читает
`props.showGrid`, `props.tool`, `props.selectedId` из замыкания — они навсегда остались
значениями с момента монтирования. Поэтому сетка рисуется всегда, подсветка выделения
залипает на первом объекте, а цвет пивота не реагирует на инструмент.

**Исправление:** живой `propsRef` (обновляется каждый рендер) внутри `draw`, либо стабильный
`draw` через `useCallback` + актуальные зависимости. Заодно поднять контраст сетки: сейчас
это `#b7c5d00d` — 5 % белого, её почти не видно даже когда она включена.

## 3. Правки по пунктам

### 3.1 Лимитер FPS

Убрать выпадающий список быстрых значений полностью. Остаётся: переключатель
«Лимит / Экран» и поле ввода с валидацией `1…240` (применение по Enter и по потере фокуса,
некорректное значение откатывается).

### 3.2 Кнопки воспроизведения

Было: пауза/воспроизведение и «один кадр». Станет: **пауза/воспроизведение** и **стоп**.

Стоп = «расстановка»: останавливает время, сбрасывает накопленное состояние stateful-функций
(`smooth`, `spring`, `autoblink`, шум) и рисует **нейтральный кадр** — все динамические
параметры в нуль (`x=y=rotation=skew=0`, `size=opacity=1`, `visible/layer` из базовой позы).
Спрайты встают ровно туда, где задана базовая поза, и их можно двигать мышью без
«уезжающей» анимации. Базовая поза не сбрасывается — иначе стоп стирал бы расстановку.

Реализация: новая операция движка `op: "neutral"` (возвращает нейтральный кадр и чистит
состояние + часы). Оверлей в это время показывает ту же нейтральную картинку.
Горячие клавиши: `K` — пауза, `Shift+K` — стоп. Шаг «один кадр» и его API (`engine.step`)
удаляются.

### 3.3 Границы и пивоты в сцене

Две независимые кнопки, каждая цикличная по трём состояниям:

| Состояние | Что рисуется |
|---|---|
| выкл | ничего |
| только выделенные | рамка/пивот выделенного объекта и его детей |
| все | все спрайты и группы |

Показываем состояние иконкой и подписью в подсказке («Границы: только выделенные»).
Группы тоже получают рамку (объединение базовых границ детей) и пивот (`base.x/base.y`).
Рамки считаются по базовой геометрии и трансформируются текущей матрицей — при 200 спрайтах
это дешёвая арифметика, но состояние «все» будет учитываться в замерах.
Настройки — часть раскладки редактора (как сетка), в пресет не попадают.

### 3.4 Сохранить / экспорт

См. раздел 1 — нужен ваш выбор варианта A или B.

### 3.5 Кнопка «Создать»

Рядом с «Открыть». Создаёт пустой пресет: холст 1000×600, имя «Без названия», без объектов,
глобальных переменных и модулей; лимит 60 FPS и настройки оверлея по умолчанию.
Нужно проверить и дописать пустые состояния: дерево, сцена (пустой холст), инспектор
(«Объект не выбран»), редактор скрипта, движок с нулём объектов.
Плюс подтверждение, если в текущем пресете есть несохранённые правки в файл — предлагаю
просто полагаться на автозейв и `Ctrl+Z` (как сейчас делает «Демо»), без модальных окон.

### 3.6 Окно захвата (вторая кнопка рядом с оверлеем)

Отдельное окно `rig-capture`, та же отрисовка, другой режим:

| | Оверлей (для OBS, браузерный источник и прозрачное окно) | Окно захвата |
|---|---|---|
| Фон | прозрачный / цвет / хромакей | по умолчанию непрозрачный цвет или хромакей |
| Прозрачность окна | да (Tauri) | не нужна, но доступна |
| Клики | пропуск (Tauri) | обычное окно, можно тянуть и закрывать |
| Задача | поверх игры, браузерный источник | «Захват окна» в OBS, Discord, Game Bar, запись экрана |

В браузере окно захвата — обычное окно с непрозрачным фоном (прозрачности браузер не даёт),
захватывается любым рекордером. В Tauri — окно без рамки с прозрачным или цветным фоном.
Размер и режим вписывания запоминаются отдельно от оверлея.

### 3.7 Скрытие панелей

Чинится причиной из 2.1. Дополнительно: кнопки переименуем в «Объекты» / «Скрипт» с иконками
и подсветкой активного состояния, чтобы было видно, что панель просто свёрнута.

### 3.8 Сетка

Чинится причиной из 2.2 + контраст сетки.

## 4. Модули и входы — самая большая часть

### 4.1 Что меняется в модели

Сейчас входы зашиты в трёх местах: `InputValues` в `types.ts`, ровно те же поля в
`InputValues` (`crates/rig-core/src/model.rs`) и жёсткий `match` по именам в
`eval_name` (`runtime.rs`). Плюс UI с фиксированными ползунками `speak`, `loudness`,
`talking`, `viseme_*`.

Предлагаю:

1. **Динамические входы в ядре.** `InputValues` = `values: Map<String, f64>` + `signals`.
   `eval_name` сначала ищет имя в этом словаре, иначе — обычная обработка (глобальные
   переменные, параметры кадров, `time`, `dt`, константы). Никаких зашитых `speak` в Rust
   не остаётся.
2. **Реестр модулей в TS** (`src/modules/`). Модуль — обычный объект:

   ```ts
   interface RigModule {
     id: "loudness" | "viseme" | string;
     name: string;
     provider: "mic" | "manual" | "plugin";
     inputs: Array<{ name: string; label: string; min: number; max: number; hint?: string }>;
     /** Для mic-модулей: обновление из кадра аудио. */
     update?(audio: AudioFrame, values: Record<string, number>): void;
   }
   ```

   В MVP два встроенных: **loudness** (`speak`, `loudness`, `db`, `talking`) и
   **viseme** (`viseme_a`, `viseme_e`, `viseme_i`, `viseme_o`, `viseme_u`). Позже тот же
   интерфейс может наполняться внешними плагинами — для этого в реестре уже будет
   провайдер `plugin`.
3. **Состояние модулей в пресете:**

   ```ts
   interface ModuleState {
     id: string;
     enabled: boolean;
     /** Какие входы модуля выключены (по умолчанию включены все). */
     disabledInputs: string[];
     /** Источник значений: живой микрофон или ручные ползунки. */
     source?: "live" | "manual";
   }
   ```

   Имя модуля неизвестно текущей сборке → показываем в списке как «недоступен», его входы
   не активируем, но состояние не теряем.
4. **Загрузка пресета: диалог вместо тихой миграции.** Пресет хранит свой набор модулей и
   входов, а при открытии показывается окно:

   > Пресету нужны модули: **Loudness** (`speak`, `talking`), **Viseme** (`viseme_a` … `viseme_u`).
   > Применить этот набор? Активные модули, которых нет в пресете, будут выключены.
   > [Применить] [Оставить как есть] [Открыть без модулей]

   - **Применить** — полная перезапись активного набора: лишние модули выключаются, чужие
     входы не висят в фоне (это ваше требование).
   - Дополнительно сканируем формулы пресета и знаем, какие входы реально используются;
     в диалоге будет галочка «только используемые входы» — она выключает объявленные, но
     не встречающиеся в скриптах входы.
   - **Оставить как есть** — набор модулей текущей сессии не меняется, отсутствующие входы
     дают нули и попадают в диагностику («вход `viseme_a` не подключён»).
   - Если модуль из пресета недоступен в этой сборке, он показывается как «недоступен»,
     а его состояние сохраняется на будущее.

   У «Создать» модулей нет — пустой пресет без лишних ползунков.
5. **Глобальные `blink`/`breath`** остаются как есть: это переменные в `globals`, не входы.

   Что такое `signal.blink` сегодня: отдельный канал `signal.<имя>` — в него пишет интерфейс
   (кнопка «моргнуть» ставит `1` на 160 мс) или внешний плагин. А `autoblink(min_ms, max_ms,
   [seed])` — не вход, а **функция движка**: она держит состояние на каждый вызов, раз в
   случайный интервал `min…max` миллисекунд открывает окно моргания длиной 120 мс и возвращает
   `1`, остальное время `0`; при фиксированном `seed` поведение детерминировано. Заменить её
   `random()` нельзя: случайное число на каждый кадр даст дрожание, а не моргание — окно
   моргания требует состояния.

   Поэтому: `autoblink` остаётся функцией ядра (входы ей не нужны), ручное моргание становится
   **входом `blink` из встроенного модуля ручных входов** («Manual», кнопка «моргнуть» +
   переключатель). `signal.*` сохраняем и документируем как канал для внешних плагинов — именно
   через него плагин сможет писать любые сигналы, не плодя входы.

   В демо-рте рот открывается от `talking`/`speak` из модуля `loudness`: если модуль выключен,
   рот закрыт, а формулы получают нули — это ожидаемо и попадёт в диагностику.

### 4.2 Вкладка «Модули»

После «Входы». Список доступных модулей, у каждого: название, описание, переключатель
включения и стрелка «развернуть» → список входов с индивидуальными переключателями.
Выключенные входы не показываются во вкладке «Входы» и не передаются в расчёт.

### 4.3 Вкладка «Входы»

Строится динамически: группа на каждый включённый модуль, внутри — только его включённые
входы. Для микромодулей: кнопка «Микрофон», индикатор уровня, переключатель
«живой / ручной» и ползунки (в ручном режиме). Виземы — обычные ползунки, пока нет реального
липсинка; когда появится — анализатор спектра в том же модуле.

Экономия ресурсов: выключенный модуль не запускает свой анализ (для визем это будет
спектр — основная стоимость), выключенный вход не попадает в словарь кадра.

### 4.4 Документация DSL

По вашему замечанию `autoblink` (и другие функции) нигде не описаны. Сделаю:

- `docs/DSL.md` — полный справочник: синтаксис, параметры объекта, `base`/динамика, единицы
  (сцена / UV / пиксели картинки), `parent`/`inherit`/`offset`/`follow`, глобальные переменные,
  входы и модули, `signal.*`, и **все функции** с сигнатурой, семантикой, состоянием и примером:

  | Группа | Функции |
  |---|---|
  | Числа | `min`, `max`, `abs`, `sign`, `round`, `floor`, `ceil`, `sqrt`, `exp`, `log`, `pow`, `mod`, `atan2` |
  | Тригонометрия | `sin`, `cos`, `tan`, `sind`, `cosd`, `tand`, `deg`, `rad` |
  | Интерполяция | `limit`, `clamp`, `lerp`, `smoothstep` |
  | Векторы | `vec`, `vadd`, `vsub`, `vmul`, `vscale`, `vlen`, `vnorm`, `vdot`, `vangle`, `rotate`, `orbit`, `follow` |
  | UV ↔ px | `px`, `uv`, `pxv`, `uvv` |
  | С состоянием | `smooth`, `spring`, `noise`, `shake`, `autoblink` |
  | Случайность | `rnd`, `random` |
  | Константы и время | `pi`, `e`, `time`, `dt`, `canvasWidth`, `canvasHeight`, `width`, `height` |

  Отдельная статья в справочнике — «состояние и время»: почему `smooth`/`spring` зависят от `dt`,
  почему порядок строк не важен, как `autoblink` планирует следующее моргание, почему
  `random()` не годится для моргания.
- README — компактная таблица-шпаргалка всех функций и ссылка на подробный справочник.
- Проверка: тест сверяет список имён функций из документации с реально зарегистрированными в
  ядре, чтобы справочник не расходился с кодом.

## 5. Порядок работ

**Фаза 1 — UI и два бага (низкий риск, без изменений формата и ядра):**
лимитер FPS, стоп вместо шага, границы/пивоты, «Создать», раскладка панелей, сетка,
файловая модель сохранения в браузере («Сохранить» / «Сохранить как…» через File System Access
API, запасной путь — скачивание файла). Регрессионные тесты Playwright на всё перечисленное.

**Фаза 2 — окна:**
окно захвата; режим `--app` в лаунчере и проверка Tauri на вашей машине; запись в папку
приложения и нативный диалог «Сохранить как…»; при необходимости доработка прозрачности
и click-through.

**Фаза 3 — модули и входы:**
динамические входы в Rust, реестр модулей, миграция пресетов, вкладки «Модули» и «Входы»,
тесты ядра на произвольные имена входов и на отсутствие зашитых имён. Это единственная часть,
которая меняет формат пресета и Rust-ядро, поэтому её лучше делать отдельным коммитом после
стабилизации UI.

## 6. Риски

- **Стоп рисует нейтральный кадр** — если в скрипте есть формулы, привязанные к `visible`
  (например, усы по углу), при стопе они не выполняются; показывается базовая поза. Считаю
  это правильным для расстановки, но это поведение стоит проговорить.
- **Модули ломают обратную совместимость** только если не сделать диалог применения набора;
  с диалогом старые пресеты открываются без сюрпризов, а «Открыть без модулей» остаётся
  аварийным вариантом.
- **Tauri нельзя проверить здесь** — сборка и захват окна проверяются на вашей машине.
- **Внешние плагины** (сторонний JS, добавляющий входы) — отдельное решение по безопасности:
  предложу грузить их только из папки приложения и с явным включением, не в MVP.
