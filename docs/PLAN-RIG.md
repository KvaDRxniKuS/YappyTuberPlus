# План: состояния, сетка и артмеш

Обсуждается. Это план, а не код. Решения из разговора зафиксированы, спорные
места помечены «решить по ходу».

Цель — приблизить риг к Live2D Cubism: у объекта есть **состояния**, привязанные к
значениям **параметров** (ползунки `manual`, входы трекеров, любые переменные —
вход, глобальная или локальная), а форма задаётся **сеткой**, которую двигают
ключи. Источник истины остаётся один: объект и его параметры; вкладка состояний
только прописывает значения — как это уже делает «Поведение».

## 1. Что решили

| Вопрос | Решение |
|---|---|
| Механизм состояний | **один**: позы с весами. «Сетка ключей» — это **редактор**, который сам считает веса из 1–2 параметров (§3) |
| Ключ | поза, вес которой вычислен из параметра; отдельной сущности «ключ» в данных нет |
| Оси | 1–2 параметра на слой-сетку |
| Ключей на ось | **два** по умолчанию (сетка 2×2); больше — та же структура данных, вопрос только интерфейса |
| Где хранится | **блок в скрипте объекта** (`# states {…}`): истина — скрипт, как у «Поведения» |
| Интерфейс | отдельная вкладка «Состояния»: режим «сетка» и режим «позы», выбор ключа кликом |
| Деформация | **сетка объекта заменяет `warp`**: `warp` — это сетка 2×2 |
| Сетка деформера | по умолчанию 2×2, максимум **32×32** |
| Артмеш | **произвольная триангуляция по трём точкам**, как в Cubism; отдельный редактор; полигон работает и как обрезка |
| Сетка на группе | **да**, деформирует детей; галка **«деформируется родителем»**; выключена — по родителю едет только пивот |
| Инструменты | кисть (радиус, жёсткость) **и** ручное перетаскивание точек; симметрия: пивот / центр сетки / центр сцены / вручную |
| Ключи двигают точки | **да**: поза и смещения точек деформера в одном ключе |
| Параметры | **любое имя**: вход, глобальная или локальная переменная объекта (§5) |
| Видимость | состояние может только **гасить** |
| Рендер | **WebGL2 для всей сцены**, текст — сразу |
| Совместимость | старые пресеты не поддерживаем, если это даёт лучший результат |

## 2. Словарь

- **Параметр** — имя, значение которого двигает состояние: `manual.value`,
  `tracker.head_rx`, `mic.speak`, глобальная `mood`, локальная `eye_target`.
- **Поза** — набор дельт полей объекта (и, если нужно, смещений точек деформера).
- **Вес** — число 0…1, «насколько поза включена».
- **Слой** — группа поз, которые смешиваются между собой по своим весам. Слои
  складываются, порядок не важен.
- **Ключ** — поза внутри слоя-сетки, вес которой посчитан из параметров.
- **Деформер** — прямоугольная сетка, которая двигает точки артмеша.
- **Артмеш** — треугольники, которыми режется картинка.

## 3. Один механизм: позы с весами

### 3.1 Почему не два

В прошлой редакции плана были «сетка ключей» и «позы с весами» как два разных
механизма. Это была ошибка: **при двух ключах на ось сетка и есть позы с весами.**

- Одна ось, два ключа: `t = (v − a₀)/(a₁ − a₀)`, веса `1 − t` и `t`. Результат
  `(1 − t)·P₀ + t·P₁` — ровно две позы с дополняющими весами. Отличить нельзя.
- Две оси, четыре ключа: веса `(1 − t₁)(1 − t₂)`, `(1 − t₁)t₂`, `t₁(1 − t₂)`,
  `t₁t₂` — ровно четыре позы с весами, сумма которых всегда 1.

То есть сетка — **частный случай** списка поз: тот, где веса считаются из
параметров автоматически, а не пишутся руками. Обратное неверно: пять эмоций с
произвольными весами в сетку 2×2 не уложить.

Отсюда решение: механизм один — **список поз с весами**. «Сетка» остаётся как
режим редактора: она создаёт 2 или 4 позы и генерирует для них веса. Разницы в
рантайме нет вообще, поэтому нет и вопроса «что выбрать».

### 3.2 Что даёт каждый режим

| | Слой-сетка | Слой-позы |
|---|---|---|
| Веса | считаются из параметров (§4) | пишет автор выражением |
| Сколько поз | 2 или 4 (по умолчанию) | сколько нужно |
| Для чего | непрерывные величины: угол головы, открытый рот | эмоции, события, приоритеты, переходы |
| Как выглядит | таблица «параметр × параметр» | список «поза · вес · значения» |
| Переход во времени | `smoothstep` по параметру | `smooth(значение, мс)` в весе |

Слой-сетку можно в любой момент «развернуть в позы» (веса станут выражениями), а
обратно — только если веса совпадают с шаблоном. Данные при этом не меняются:
и там, и там список поз.

### 3.3 Сумма или среднее

Две включённые позы **могут** дать сумму — я зря подал усреднение как свойство
механизма. Это настройка слоя:

| `normalize` | Формула | Когда |
|---|---|---|
| `sum` (по умолчанию) | `Σ wᵢ·Pᵢ` | как в Cubism: параметры складываются, слои не спорят |
| `average` | `Σ wᵢ·Pᵢ / Σ wᵢ` | кроссфейд эмоций: «грусть + злость» — смесь, а не двойной наклон |

У слоя-сетки сумма весов всегда 1, поэтому оба режима дают одно и то же — и это
хорошая проверка, что сетка не «раздувает» позу.

### 3.4 Чем это отличается от настоящего keyform

Разница не в сетке и не в весах, а в том, **что хранит ключ**:

| | Настоящий keyform (Cubism) | Blendshape |
|---|---|---|
| Значения | **абсолютные**: где вершина и как стоит объект при этом значении параметра | **дельты**: насколько сдвинуть от текущего |
| Слои | вычисляются по порядку деформеров, каждый следующий видит результат предыдущего | складываются |
| Что умеет | полностью переписать форму: переставить вершины, сменить точку вращения | добавить движение к авторскому |

Мы делаем **дельты**: иначе состояния начнут спорить с инспектором, «Поведением» и
авторскими формулами — а это против правила «истина — объект и его параметры».
Ключи у нас действительно ближе к blendshape, и это осознанно.

Если когда-нибудь понадобится «поза целиком вместо авторской», у слоя появится
`mode: "replace"` — данные это позволяют (поза уже набор полей, а не приращение к
формуле). Сейчас такого требования нет.

### 3.5 Как складывается

Внутри слоя позы смешиваются по весам, между слоями результат складывается, и всё
вместе прибавляется к авторской позе:

```
поле = авторское + <поле>_behaviour + <поле>_states
```

Правила соединения — те же, что у каналов `<поле>_behaviour` (единообразие не
случайное):

| Поле | Как соединяется |
|---|---|
| `x`, `y`, `rotation`, `skewX`, `skewY` | **сложение** |
| `sizeX`, `sizeY` | `1 + Σ wᵢ·(sizeᵢ − 1)` — складываются отклонения от единицы |
| `opacity` | то же, отклонения от единицы |
| `visible` | **произведение** `Π (1 − wᵢ·(1 − vᵢ))`: состояние только гасит |

## 4. Слой-сетка

### 4.1 Данные

```json
{"kind":"grid",
 "axes":[{"param":"manual.value","at":[0,1]},
         {"param":"head_rx","at":[-30,30]}],
 "smooth":true,
 "poses":[{"at":[0,0],"pose":{"y":0}},
          {"at":[1,0],"pose":{"y":-6}},
          {"at":[0,1],"pose":{"rotation":4}},
          {"at":[1,1],"pose":{"y":-6,"rotation":-8}}]}
```

- `at` — положение ключа в нормированных координатах (0 или 1 по каждой оси).
- Внутри ячейки — **билинейно** (с одной осью — линейно). `smooth` меняет линейный
  ход на `smoothstep`, чтобы у ключа не было излома.
- `pose` — дельты к авторской позе.
- Точки деформера в ключе — в том же объекте `pose` (`points`, §6.4).

### 4.2 Генерируемый код

```
# states {"format":1,"layers":[{"kind":"grid", …}]}
t1 = smoothstep(0, 1, clamp((manual.value - 0) / (1 - 0), 0, 1))
t2 = smoothstep(0, 1, clamp((head_rx + 30) / 60, 0, 1))
w_00 = (1 - t1) * (1 - t2)
w_10 = t1 * (1 - t2)
w_01 = (1 - t1) * t2
w_11 = t1 * t2
y = inherit + y_behaviour + y_states
```

`<поле>_states` собирается из весов и значений поз. Блок — источник истины;
генератор перезаписывает **только свои** строки (`t*`, `w_*`, `<поле>_states`),
авторские формулы не трогает. Ровно так уже работает «Поведение».

### 4.3 Больше двух ключей

Структура данных не мешает: третий ключ — это ещё одна поза со своим `at` и
кусочно-линейными весами. Предел «два» — про интерфейс первой версии, а не про
формат. Когда понадобится, сетка просто станет таблицей большего размера.

## 5. Параметры — любые имена

Слой может ссылаться на любое имя скрипта: вход модуля, глобальная переменная,
**локальная переменная объекта**.

Позы считаются сгенерированным кодом, поэтому для них **правки ядра не нужно**:
имена резолвит сам скрипт.

Точки сетки считает рендерер, а он переменных скрипта не видит. Поэтому ядро
научится отдавать наружу значения нужных имён:

- в структуре объекта — список `watch` (какие имена нужны слоям);
- в кадре — `vars` у объекта: `{"eye_target": 3, "mood": 0.4}`.

Это же даёт побочную возможность, о которой вы говорили: **видно локальные
переменные объектов** — их можно показать в панели «Входы» и в предупреждениях,
не заходя в скрипт.

| Слот | Что меняется |
|---|---|
| ядро | **+1**: поле `watch` в структуре и `vars` в кадре (новый контракт) |

Пересборка ядра (`app-update`) делается на вашей машине: в песочнице нет `cargo`,
поэтому новый WASM я собрать не смогу — проверять придётся у вас, и это стоит
заложить в этап (§11).

## 6. Сетка и артмеш

### 6.1 Две разные вещи

| | Артмеш | Деформер |
|---|---|---|
| Что задаёт | **как** режется картинка: треугольники по точкам | **что стало** с этими треугольниками |
| Форма | произвольная триангуляция | прямоугольная сетка `cols × rows` |
| Редактор | свой: точки, треугольники, автосетка | свой: точки сетки, кисть |
| Ключи | не двигают | **двигают** (ключ хранит смещения точек) |

Артмеш решает вторую задачу, о которой вы сказали: у хвоста и произвольной формы
прямоугольник «мажет» прозрачными углами, а полигон рисуется ровно по контуру.

### 6.2 Данные

```ts
interface MeshSpec {
  /** Как режется картинка: точки и треугольники по ним. Координаты 0…1. */
  art: ArtMesh;
  /** Деформер: прямоугольная сетка. Нет — артмеш рисуется как есть. */
  deform: GridSpec | null;
}

interface ArtMesh {
  points: Vec2[];        // в долях картинки
  triangles: number[];   // тройки индексов точек
  /** Контур внешних точек — для автотриангуляции и показа. */
  outline?: number[];
  /** Автосетка grid: какие деления её породили (нет — ручной меш). */
  auto?: { cols: number; rows: number } | null;
}

interface GridSpec {
  cols: number;          // 2…32
  rows: number;          // 2…32
  points: Vec2[];        // порядок: слева-вправо, сверху-вниз
}
```

UV не нужны отдельно: точки лежат на плоскости картинки, поэтому текстурная
координата совпадает с положением точки (0…1). Это верно и для произвольного
полигона — он всё равно вырезан из той же картинки.

`art: 2×2` — сегодняшний `warp` с неподвижными углами. Поле `warp` больше не
пишется: при открытии старого пресета четыре угла переезжают в `art.points`.

### 6.3 Деформер двигает артмеш

Точка артмеша попадает в ячейку деформера и билинейно переносится вместе с её
четырьмя углами. Точки за пределами сетки прилипают к ближней ячейке. Деформер не
меняет картинку сам по себе: на регулярной сетке результат совпадает с недеформированным
объектом.

Ключи двигают точки **деформера**, а не артмеша: артмеш — это «как нарезано»,
деформер — «что с этим стало». Ключ не зависит от плотности артмеша, и его не надо
переписывать, когда автор поднял качество сетки.

### 6.4 Ключ, двигающий точки

```json
{"at":[0,1],"pose":{"rotation":4},
 "points":{"3":[-0.02,0.01],"4":[0.03,0.0]}}
```

- Хранятся **смещения** только тронутых точек; индекс — `j·(cols+1) + i` в сетке
  деформера.
- Интерполяция — та же, что у позы: билинейная по сетке или по весам.
- Ключи живут **в том же блоке `# states`**. Ядро блок не читает (это
  комментарий), точки считает редактор и передаёт рендереру.

### 6.5 Иерархия

У объекта есть галка **«деформируется родителем»** (по умолчанию включена).

| Состояние галки | Что происходит |
|---|---|
| включена | точки объекта (артмеш после своего деформера) прогоняются через деформер родителя — форма гнётся вместе с родителем |
| выключена | через деформер родителя проходит только **пивот**: берётся треугольник родителя, в который он попал, и объект едет и поворачивается жёстко, форму не меняя |

Второй режим — для «голова гнётся, а зрачок в глазу не растягивается». Группа
деформирует детей так же, как спрайт: правил два, и они одни на все виды.

## 7. Инструменты

### 7.1 Общие для сетки и артмеша

| Инструмент | Что делает |
|---|---|
| Перетаскивание точки | тянет одну точку; `Shift` — по осям |
| Кисть | двигает точки в радиусе; жёсткость — линейная, сглаженная (`smoothstep`) или постоянная; сила 0…100 % |
| Сглаживание | лапласиан по выделенным точкам: убирает «зубцы» после кисти |
| Симметрия | ось выбирается: **пивот**, **центр сетки**, **центр сцены**, **вручную** (ось проводится по сцене) |
| Закрепить | точка не двигается кистью |
| Сброс | регулярная сетка / исходный меш |
| Показ | точки, рёбра, заливка жёсткости кисти |

Любой жест (протяжка) — **один шаг истории**, а не сорок.

### 7.2 Редактор артмеша

- **Автосетка**: `cols × rows` по картинке (то, что нужно в 90 % случаев).
- **Ручной меш**: расставить точки по контуру, разрезать ребро, добавить и удалить
  точку, добавить треугольник, перевернуть диагональ у двух соседних.
- **Автотриангуляция контура** (метод «отрезания уха») как начало: нарисовал
  контур — получил треугольники, дальше правишь руками.
- Проверка: точки внутри картинки, треугольники не пересекаются, нет «дыр» —
  иначе объект молча рисуется кусками.

## 8. Рендер и производительность

Сегодня сцена рисуется Canvas 2D, а свет — отдельным WebGL2-проходом на слой.
`warp` рисуется двумя треугольниками через `clip` + `drawImage`; сетка так не
масштабируется: 6×6 — это 72 клипа на объект на кадр.

Решение: **один WebGL2-рендер всей сцены**, сразу со всеми видами объектов.

| Что | Как в WebGL2 |
|---|---|
| Спрайт, медиа | текстура + индексный буфер треугольников артмеша |
| Фигура | триангуляция контура (`tracePath` уже даёт путь) |
| Текст | строчка рисуется в маленькую канву и уходит текстурой, кэш «строка + стиль» |
| Маска | трафарет (stencil) или `discard` по маске-текстуре |
| Свет, материал, нормали | шейдеры переезжают в тот же проход, без второй канвы |

Служебные рамки редактора (сетка, ручки, подписи) остаются на отдельной Canvas
2D-канве **сверху** — они не часть кадра и в оверлей не едут.

**Связь с бэклогом §4.** В OBS без аппаратного ускорения WebGL2 уходит в
программный растеризатор — значит новый рендер сделает «свет лагает» заметнее.
Поэтому передача готового кадра из редактора (`docs/BACKLOG.md` §4) идёт **вместе**
с этой работой: сначала рендер, сразу за ним — картинка в OBS.

## 9. Вкладка «Состояния»

```
┌ Слои ──────────────────────────────────────────────┐
│ [сетка] manual.value × head_rx              [+]    │
│ [позы]  sad, angry, cry                            │
├ Ключи ─────────────────────────────────────────────┤
│        head_rx −30        head_rx +30              │
│ 0.0   [ключ 1: y 0]       [ключ 2: y −4]           │
│ 1.0   [ключ 3: y 12]      [ключ 4: y 6]            │
├ Значения ключа ────────────────────────────────────┤
│ y −4  rotation 0  size 1.00 …      [Записать позу] │
└────────────────────────────────────────────────────┘
```

- **Выбор ключа** — клик по ячейке (в режиме поз — по строке списка).
- **«Записать позу»** — берёт текущее состояние объекта (как он стоит в сцене и
  как двигали точки) и пишет **дельты** от авторской позы в выбранный ключ.
- **Проверочный ползунок** на каждой оси двигает ключи в редакторе, не трогая
  настоящий вход. Живой вход (ползунок `manual`) работает сразу.
- Пустой ключ — нулевые дельты, то есть «как в инспекторе»: это нормальное
  состояние, а не ошибка.

|---|---|
| ядро | **+1**: `watch` в структуре, `vars` в кадре — состояния могут брать локальные переменные (и их видно в панели) |
| файл | **8**: `mesh` вместо `warp`; старые пресеты мигрируют при открытии, новый редактор их читает, старый новые — нет |
| мост | **+1**: `vars` и сетка в кадре — старая страница в OBS нарисовала бы объект недеформированным молча |
| оболочка | **+1**: новый рендер, вкладка «Состояния», редакторы сетки и артмеша |

## 11. Этапы

1. **Ядро и данные.** `watch`/`vars` в ядре (сборка WASM на вашей машине),
   `MeshSpec` в типах, миграция `warp` → 2×2, блок `# states` (разбор и запись).
2. **Рендер WebGL2.** Спрайты, медиа, фигуры, текст, маски, материал и свет —
   в одном проходе. Сцена выглядит как раньше (проверка по скриншотам).
3. **Редактор сетки и артмеша.** Показ точек и треугольников, перетаскивание,
   кисть, сглаживание, симметрия (4 оси), сброс; автосетка и ручной меш;
   галка «деформируется родителем» и деформер группы.
4. **Ключи.** Вкладка «Состояния», режим сетки (1–2 оси), «записать позу»,
   проверочные ползунки, генератор кода.
5. **Ключи точек.** Смещения деформера в ключах, `vars` в мосте.
6. **Позы и приоритеты.** Режим «позы», веса выражениями, `sum`/`average`,
   плавные переходы.

## 12. Что осталось решить

1. **`sum` или `average` по умолчанию?** Предлагаю `sum` (как в Cubism); режим
   `average` доступен на слое.
2. **Нужен ли `mode: "replace"`** (поза вместо авторской) или хватает дельт?
3. **Сколько слоёв** разрешать на объект (2, 4, без предела).
4. **Кисть**: двигает по нормали к сетке или свободно в плоскости? Предлагаю
   свободно (как в Cubism), с `Shift` по осям.
5. **Симметрия вручную**: ось рисуется на сцене и живёт в профиле или в пресете?
