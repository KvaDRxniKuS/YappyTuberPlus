# План: состояния, сетка объекта и артмеш

Обсуждается. Это план, а не код: решения из разговора зафиксированы, спорные
места помечены «решить по ходу». Ничего не начинаем, пока не договорим.

Цель — приблизить риг к Live2D Cubism: у объекта есть **состояния**, привязанные
к значениям **параметров** (ползунки `manual`, входы трекеров, любые другие входы),
а форма задаётся **сеткой**, которую двигают ключи. Источник истины остаётся один:
объект и его параметры; вкладка состояний только прописывает значения — как это
уже делает вкладка «Поведение».

## 1. Что решили

| Вопрос | Решение |
|---|---|
| Модель состояний | **сетка ключей** (как в Cubism), но не больше **двух осей**, и по каждой оси ровно **два ключа** → сетка не больше 2×2 |
| Позы с весами | делаем **дополнительно**, как второй вид слоя (см. §5) |
| Где хранится | **блок в скрипте объекта** (`# states {…}`): истина — скрипт, как у «Поведения» |
| Интерфейс | **отдельная вкладка** «Состояния»: таблица слоёв, сетка ключей, «записать позу», выбор ключа |
| Деформация | **сетка объекта заменяет `warp`**: `warp` — это сетка 2×2 |
| Артмеш | **да**: своя сетка отрисовки; её точки двигаются деформером |
| Сетка на группе | **да**, деформирует детей; галка **«деформируется родителем»**; выключена — по родителю едет только пивот |
| Инструменты точек | **оба**: кисть (радиус, жёсткость) и ручное перетаскивание, как в Cubism |
| Ключи двигают точки | **да**, ключ = поза + точки деформера |
| Совместимость | старые пресеты не поддерживаем, если это даёт лучший результат |
| Производительность | решает новый рендер; Canvas 2D на треугольник не тянет (см. §8) |

## 2. Словарь

- **Параметр (ось)** — имя, значение которого двигает состояние: `manual.value`,
  `tracker.head_rx`, `mic.speak`, константа пресетов. Для сетки ключей: ось + две
  границы, между которыми значение нормируется в 0…1.
- **Ключ (keyform)** — набор значений для одной точки сетки: «при этом значении
  оси объект выглядит так».
- **Слой состояний** — одна независимая таблица ключей: сетка (1–2 оси) или набор
  поз с весами. Слои складываются, порядок не важен.
- **Деформер** — сетка, которая двигает точки артмеша.
- **Артмеш** — сетка отрисовки: по ней картинка режется на треугольники.

## 3. Оси и параметры

Параметр — имя из входов (`InputValues.values`): всё, что дают модули, плюс
константы пресетов. Ползунки `manual` — не особый случай, а просто один из входов,
поэтому «вместо ползунков любые переменные и входы» получается само собой.

| Вид ключа | Какие имена допустимы | Почему |
|---|---|---|
| ключ **позы** | любое имя скрипта (`manual.value`, `tracker.head_rx`, `time`, локальная переменная) | поза считается сгенерированной формулой в скрипте, а имена резолвит ядро |
| ключ **точек сетки** | только **входы** | точки считает рендерер: значения осей он получает в кадре (`frame.vars`), а переменные скрипта наружу не выходят |

Ограничение по именам — единственное, что нам придётся соблюдать. Если
понадобится двигать точки переменной скрипта, это уже правка ядра (оно должно
отдавать значения наружу), и её лучше обсуждать отдельно.

Ось задаётся тремя числами: `param`, `at: [a0, a1]`. Значение нормируется
`t = clamp((v − a0) / (a1 − a0), 0…1)`, поэтому всё, что за границами, просто
прилипает к крайним ключам. Инверсия — это просто `at: [1, 0]`.

## 4. Сетка ключей

### 4.1 Данные

```json
{"kind":"grid",
 "axes":[{"param":"manual.value","at":[0,1]},
         {"param":"tracker.head_rx","at":[-30,30]}],
 "smooth":true,
 "keys":[{"at":[0,0],"pose":{"y":0}},
         {"at":[1,0],"pose":{"y":-6}},
         {"at":[0,1],"pose":{"rotation":4}},
         {"at":[1,1],"pose":{"y":-6,"rotation":-8}}]}
```

- `at` — положение ключа в сетке в нормированных координатах (0 или 1 по каждой
  оси). С двумя осями ключей четыре; с одной — два.
- Внутри ячейки — **билинейная интерполяция** (с одной осью — линейная).
  Галочка `smooth` меняет линейный ход на `smoothstep`, чтобы у ключа не было
  излома на глаз.
- `pose` — **дельты** к авторской позе, а не абсолютные значения. Иначе состояния
  спорили бы с формулами и с «Поведением».

### 4.2 Как складывается

Правила те же, что у каналов `<поле>_behaviour` — это не совпадение, а
сознательное единообразие:

| Поле | Как соединяется |
|---|---|
| `x`, `y`, `rotation`, `skewX`, `skewY` | **сложение** |
| `sizeX`, `sizeY`, `opacity` | **произведение** (в ключе хранится множитель, 1 — как есть) |
| `visible` | **минимум**: состояние может гасить, но не может включить скрытое формулой |

Слои складываются: `поле = авторское + <поле>_behaviour + <поле>_states`.

### 4.3 Генерируемый код

```
# states {"format":1,"layers":[{"kind":"grid", …}]}
y = inherit + y_behaviour + y_states
x = inherit + x_behaviour + x_states
```

Блок — источник истины; генератор перезаписывает **только свои** строки (помечены
именем `<поле>_states`), авторские формулы не трогает. Ровно так уже работает
«Поведение», и это правило придётся сохранить: правишь блок руками — таблица
перечитывается, правишь таблицу — блок и строки перезаписываются.

Новых функций ядра не нужно: `lerp`, `clamp`, `smoothstep` есть с первого
поколения. **Ядро не меняется.**

## 5. Позы с весами (вариант C) — механизм

### 5.1 Чем отличается от сетки

| | Сетка ключей (B) | Позы с весами (C) |
|---|---|---|
| Что задаёт состояние | **где** стоит параметр на оси | **насколько** каждая поза «включена» |
| Сколько поз сразу | одна точка в сетке (смесь соседних ключей) | сколько угодно, все суммируются |
| Хорошо для | непрерывных величин: угол головы, открытый рот | именованных состояний: грусть, злость, крик |
| Плохо для | эмоций «или-или» — нужна ось на каждую | непрерывных величин — вес пришлось бы считать вручную |

Поэтому они не заменяют друг друга: сетка — «мимика от угла», веса — «эмоция».

### 5.2 Как считается

У каждой позы есть **вес** — выражение 0…1, и **дельты** (те же поля, что у ключа).
Смешивание — нормированная сумма:

```
W = w₁ + w₂ + … + wₙ
поза_state = (w₁·поза₁ + w₂·поза₂ + …) / max(1, W)
```

Деление на `max(1, W)` — важная мелочь: пока весов меньше единицы, поза
«проявляется» пропорционально, а лишние веса не раздувают дельты. При `W = 0`
объект стоит ровно в авторской позе.

Вес — обычное выражение, например:

| Что нужно | Вес |
|---|---|
| Плавное включение эмоции с задержкой 300 мс | `smooth(manual.sad, 300)` |
| Эмоция по настроению 0…1 | `smoothstep(0.2, 0.5, manual.mood)` |
| Крик перебивает грусть | `w_cry = smooth(manual.cry, 150)`, `w_sad = smooth(manual.sad, 300) * (1 - w_cry)` |
| Состояние из модуля пресетов | `smooth(presets_1_angry, 250)` |

Последняя строка — то, чего не хватает сегодня: смена «пресета поведения» уже
переключает константу, а плавного перехода между позами нет. C его даёт одним
полем веса.

### 5.3 Как выглядит в блоке

```json
{"kind":"blend",
 "poses":[
   {"name":"sad","weight":"smooth(manual.sad, 300)","pose":{"y":-8,"rotation":-3}},
   {"name":"angry","weight":"smooth(manual.angry, 150)","pose":{"y":2,"sizeX":1.04}}]}
```

Генератор пишет для каждой позы вес во временную переменную (`w_sad`, `w_angry`),
затем `y_states` как нормированную сумму. Имена весов не пересекаются с языком —
префикс `w_` зарезервирован генератором.

## 6. Сетка объекта и артмеш

### 6.1 Данные объекта

```ts
interface MeshSpec {
  /** Сетка отрисовки: по ней картинка режется на треугольники. */
  art: GridSpec;
  /** Деформер: сюда переезжают точки артмеша. Нет — артмеш рисуется как есть. */
  deform: GridSpec | null;
}

interface GridSpec {
  cols: number;              // делений по X
  rows: number;              // делений по Y
  /** Точки в долях картинки, 0…1; порядок — слева-вправо, сверху-вниз. */
  points: Vec2[];
}
```

- Точки по умолчанию регулярные: `(i/cols, j/rows)`.
- `art: 1×1` — плоская картинка, `2×2` — сегодняшний `warp` с неподвижными
  углами. Поле `warp` больше не пишется: при открытии старого пресета четыре угла
  переезжают в `art.points` сетки 2×2.
- Ячейка артмеша = два треугольника. Рисуется **всё** — маска, нормали, материал
  тоже считаются по этим треугольникам.

### 6.2 Как деформер двигает артмеш

Точка артмеша попадает в ячейку деформера и билинейно переносится вместе с её
четырьмя углами. Деформер не меняет картинку сам по себе: если его точки стоят на
регулярной сетке, результат совпадает с недеформированным объектом.

Ключи (§7) двигают точки **деформера**, а не артмеша: артмеш — это «сколько
треугольников», деформер — «что с ними стало». Так ключ не зависит от плотности
артмеша, и его не надо переписывать, когда автор поднял качество сетки.

### 6.3 Иерархия

У объекта есть галка **«деформируется родителем»** (по умолчанию включена).

| Состояние галки | Что происходит |
|---|---|
| включена | точки объекта (артмеш после своего деформера) прогоняются через деформер родителя — форма ребёнка гнётся вместе с родителем |
| выключена | через деформер родителя проходит только **пивот** ребёнка: берётся треугольник родителя, в который попал пивот, и ребёнок едет и поворачивается жёстко, не меняя формы |

Второй режим нужен для «голова гнётся, а зрачок в глазу не растягивается».
Группа деформирует детей так же, как спрайт: разницы в правилах нет.

### 6.4 Инструменты

| Инструмент | Что делает |
|---|---|
| Перетаскивание точки | Тянет одну точку мышью; `Shift` — по осям, `Alt` — симметрично |
| Кисть | Двигает точки в радиусе; жёсткость — линейная, сглаженная (`smoothstep`) или постоянная; сила 0…100 % |
| Сглаживание | Лапласиан по выделенным точкам: убирает «зубцы» после кисти |
| Симметрия | Зеркалит правки по вертикальной оси объекта |
| Закрепить | Точка не двигается кистью (углы рамки, например) |
| Сброс | Возврат к регулярной сетке: отдельно артмеш, отдельно деформер |
| Показ сетки | Точки, треугольники, заливка жёсткости кисти |

Все правки — шагами истории: жест (протяжка) — один шаг, а не сорок.

## 7. Ключи, двигающие точки

Ключ становится «поза + точки деформера»:

```json
{"at":[0,1],"pose":{"rotation":4},
 "points":{"3":[-0.02,0.01],"4":[0.03,0.0]}}
```

- Ключ хранит **смещения** только тех точек, которые двигали: остальные стоят на
  месте. Индекс точки — в сетке деформера (`j * (cols+1) + i`).
- Интерполяция — та же, что у позы: билинейная по сетке или нормированная сумма
  по весам. Один и тот же слой двигает и позу, и точки, поэтому «наклон головы →
  форма рта» настраивается в одном месте.
- Ключи точек живут **в том же блоке `# states`**. Ядро блок не читает (это
  комментарий), точки считает редактор и передаёт результат рендереру. Поэтому
  новых параметров в языке не появляется.
- В кадр для оверлея едут **значения осей** (`frame.vars`), а не сотни точек:
  оверлей считает ту же интерполяцию тем же кодом (`src/render/mesh.ts`).

## 8. Рендер и производительность

Сегодня сцена рисуется Canvas 2D, а свет — отдельным WebGL2-проходом на слой.
`warp` рисуется двумя треугольниками через `clip` + `drawImage`; на сетку это не
масштабируется: 6×6 — уже 72 клипа на объект, 60 кадров в секунду и десяток
объектов — это десятки тысяч клипов в секунду, Canvas 2D такого не держит.

Решение: **один WebGL2-рендер всей сцены**.

| Слой | Как рисуется в WebGL2 |
|---|---|
| Спрайт, медиа | текстура + индексный буфер треугольников артмеша; UV берутся из регулярной сетки |
| Маска | трафарет (stencil) или `discard` по маске-текстуре |
| Свет, материал, нормали | уже шейдеры; переезжают в тот же проход, без второй канвы |
| Фигура | триангуляция контура (`tracePath` уже даёт путь) |
| Текст | строчка рисуется в маленькую канву и уходит текстурой, кэш по «строка + стиль» |

Этапы перевода (каждый — рабочий продукт, а не «всё или ничего»):

1. Холст WebGL2, спрайты и медиа, свет и материал.
2. Маски и фигуры.
3. Текст.
4. Служебные рамки редактора остаются на отдельной Canvas 2D-канве **сверху**
   (сетка, ручки, подписи) — они не часть кадра и в оверлей не едут.

**Связь с бэклогом §4.** В OBS без аппаратного ускорения WebGL2 уходит в
программный растеризатор — то есть новый рендер сделает проблему «свет лагает»
ещё заметнее. Поэтому пункт «готовый кадр из редактора» (`docs/BACKLOG.md` §4)
становится основным путём для OBS, и делать их надо вместе: сначала рендер, потом
передача картинки.

Пределы: пока Canvas 2D — не больше 6×6 (и предупреждение); после WebGL2 —
32×32 на объект, 8×8 по умолчанию.

## 9. Вкладка «Состояния»

```
┌ Слои ─────────────────────────────────────────────┐
│ [сетка] manual.value × tracker.head_rx      [+]  │
│ [веса]  sad, angry, cry                          │
├ Ключи ────────────────────────────────────────────┤
│      head_rx −30        head_rx +30               │
│ 0.0  [ключ 1: y 0]      [ключ 2: y −4]            │
│ 1.0  [ключ 3: y 12]     [ключ 4: y 6]             │
├ Значения ключа ───────────────────────────────────┤
│ y −4   rotation 0   size 1.00 …  [Записать позу]  │
└───────────────────────────────────────────────────┘
```

- **Выбор ключа** — клик по ячейке; справа — его значения. Ручки те же, что в
  инспекторе (позиция, поворот, размер, прозрачность), плюс точки деформера.
- **«Записать позу»** — берёт текущее состояние объекта (как он стоит в сцене и
  как двигали точки) и пишет **дельты** от авторской позы в выбранный ключ.
- **Проверочный ползунок** у каждой оси: двигает ключи в редакторе, не трогая
  настоящий вход. Живой вход (ползунок `manual`) работает сразу, как обычно.
- Пустой ключ — нулевые дельты, то есть «как в инспекторе». Это не ошибка и не
  требует заполнения.

## 10. Версия и совместимость

| Слот | Что меняется |
|---|---|
| файл | **8**: `mesh` вместо `warp`; старые пресеты мигрируют при открытии, но старый редактор новые не прочитает |
| оболочка | **+1**: новый рендер, вкладка «Состояния», редактор сетки |
| мост | **+1**: `frame.vars` и сетка в кадре — старая страница в OBS нарисует объект без деформации молча, а этого быть не должно |
| ядро | **без изменений**: `*_states` — обычные формулы, `warpTLx…` остаются в языке как устаревшие |

## 11. Этапы

1. **Модель и рендер.** `MeshSpec` в типах, миграция `warp` → 2×2, WebGL2-рендер
   спрайтов и мешей, свет внутри него. Сцена выглядит как раньше.
2. **Редактор сетки.** Показ точек и треугольников, перетаскивание, кисть,
   сглаживание, симметрия, сброс; галка «деформируется родителем» и деформер
   группы.
3. **Ключи позы.** Блок `# states`, генератор, вкладка «Состояния», сетка 1–2 осей,
   «записать позу», проверочные ползунки.
4. **Ключи точек.** Смещения деформера в ключах, `frame.vars` в мосте.
5. **Позы с весами.** Слой `blend`, веса-выражения, плавные переходы, приоритеты.

## 12. Что решить до начала

1. **Ключи точек — только входы?** (переменные скрипта наружу не выходят; иначе
   нужна правка ядра).
2. **Видимость**: состояние только гасит (минимум) — согласны?
3. **Пределы сетки**: 8×8 по умолчанию, 32×32 максимум — хватит?
4. **Артмеш — только прямоугольная сетка?** В Cubism контур произвольный; у нас
   картинка прямоугольная, и я бы начал с сетки.
5. **Сколько слоёв состояний** разрешать на объект (2? 4? без предела — но UI
   длиннее).
6. **Текст в WebGL2** — сразу в этап 1 или отдельным этапом 3, как в §8?
